## 1. 要件（issue 本文の要点）

### issue #29: DST でブローカー時刻が逆行するとき Bar が約1時間欠落する

`BarBuilder` はバケツの割り当てと確定を broker 時刻だけで判断する（ADR-005）。恒常オフセットは
これで正しく扱えるが、**オフセット自体が変わる瞬間**は扱えない。OANDA の MT5 サーバーは米国夏時間に
追随し UTC+3（夏）/ UTC+2（冬）を切り替えるため、夏時間終了時に `tick.time` が約 1 時間逆行する。

開いているバケツを B（broker 時刻 `[T, T+60)`）とすると、逆行後の tick は:

- `bucket_start(tick.time)` が `B.start` より前 → 畳み込まれない
- `tick.time >= B.start + 60s` が成立しない → B が確定しない
- `bucket is None` でないので新しいバケツも開かない

結果、**broker 時刻が元の位置まで戻るまでの約 1 時間、全 tick が straggler として捨てられ、
その分の Bar が欠落する。** B の `known_at` も 1 時間遅れる。

難しい点: 単一の tick では「DST の逆行」と「順序が入れ替わって届いた 1 本の古い気配値」を区別できない。
後者で開いているバーを確定させると、既に戦略へ渡したローソク足を書き換える危険があり、
これは `tests/unit/test_bar_builder.py::test_a_straggler_from_an_older_bucket_neither_joins_nor_closes`
で明示的に禁じている挙動。

issue が挙げた対応方針の候補（採用するのは 1 番目）:

- **逆行の検出**: バケツ開始より一定以上（例: 30 分）前へ跳んだら clock jump と判断して確定・再開する
- 経過時間による staleness guard（不採用）

### issue #12: clock skew 下で broker 時刻が先行する tick を次バケツの Bar へ反映する

PR #10 時点の `BarBuilder` は、畳み込みを `known_time <= 自分のバケツ終端`、確定を
`known_time >= 開いているバケツの終端` で判断していた。この頃は、broker 時計が受信時計より進んだ
環境で「次バケツの broker 時刻を持つ tick」が Bar 構築から除外されていた（tick 系列には残る）。
issue の要求は **その先行 quote を、本来属する次バケツの OHLC へ反映すること**。

**現状の確認結果（この計画の前提）**: ADR-005（PR #28）で畳み込みも確定も `tick.time`（broker）
基準に変わったため、先行 quote は「開いているバケツを確定させ、自分のバケツを開く」ようになっており、
issue #12 が求めた「次バケツの Bar へ反映する」は**すでに満たされている**。
ただし回帰テストが無く、ADR-005 の変更で守られていることが誰にも見えない。

残る限界（今回は直さない。§7 参照）: 先行 quote が旧バケツを確定させたあとに、その旧バケツ宛ての
quote が遅れて届くと straggler として捨てられる。これを直すには開いているバケツを複数持つ必要があり、
`on_tick` の戻り値を `Bar | None` から複数 Bar へ変えることになる（backtest engine を含む
7 箇所の呼び出し側に波及する）。今回のスコープ外。

### issue #33: 急変時にライブ Bar がポーリングの取りこぼしで極値を落とす

collector のポーリングは 200ms 間隔（`tick_poll_interval_seconds`）で、`symbol_info_tick` は
1 回につき最新 1 本しか返さない。したがって**毎秒 5 本を超える速度で気配値が来る局面では取りこぼす**。
実測（2026-08-24 ロンドン時間）では約 47 本/分で取りこぼしはほぼ無いが、指標発表・介入・急変時は
秒間数十本が飛んでくる。そこはちょうど高値・安値が意味を持つ場面でもある。

結果、ライブの Bar は急変時に極値を取り逃した OHLC になりうる。後から backfill で完全な tick が
入っても、`ON CONFLICT DO NOTHING` と再開位置により、その Bar は二度と読み直されない。

issue が挙げた候補:

1. 閉じたバケツを `copy_ticks_range` から組む（bar_service が MT5 に依存する点が論点）
2. リビジョンとして追記する（`UNIQUE (symbol, timeframe, start_at)` の撤廃を含むスキーマ変更 → ADR 必要）
3. ポーリング間隔を詰める（対症療法）

**採用する方針**: 候補 1 の変種として、**bar_service ではなく collector 側**でポーリングの
取りこぼしを埋める。collector は既に MT5 モジュールと `copy_ticks_range` を持っているので、
「bar_service が MT5 に依存する」という論点が消える。stored tick 系列が完全になれば、
そこから畳む bar_service も backtest も自動的に正しい極値を得る（スキーマ変更ゼロ）。

## 4. 実装 1: broker clock の逆行検出（issue #29）

`src/trading/data/market/bars.py`

### 4-1. モジュール定数を追加する

`bucket_start` の直前あたり、モジュール先頭の定数として置く:

```python
# How far the broker's clock may step backwards before it is read as the
# server leaving summer time rather than a quote arriving out of order. The
# shift is a whole hour twice a year (ADR-032); reordering inside the feed is
# seconds wide, so nothing legitimate lands between the two.
CLOCK_STEP_BACK = timedelta(minutes=30)
```

`timedelta` は既に import 済み。

### 4-2. `BarBuilder.on_tick` に逆行の分岐を足す

現在の `on_tick` の冒頭（`start = bucket_start(...)` と `bucket = self._bucket` の直後）に、
既存のロジックより前に置く:

```python
        if bucket is not None and self._stepped_back(bucket, start, tick):
            # The broker clock moved, it did not deliver late: a quote this
            # far behind the bucket's own quotes is the server leaving summer
            # time. Publishing the open bucket and starting again on the new
            # position keeps bars flowing; holding it would drop every quote
            # until the clock climbed back (ADR-032).
            completed = self._to_bar(bucket, tick.known_time)
            self._bucket = _open_bucket(start, tick)
            return completed
```

そして private メソッドを足す（`_end_of` の隣）。`start` は呼び出し側で計算済みのものを渡す
（同じ値を 2 回計算しない）:

```python
    @staticmethod
    def _stepped_back(bucket: _Bucket, start: datetime, tick: Tick) -> bool:
        return start < bucket.start and tick.time <= bucket.last_time - CLOCK_STEP_BACK
```

判定の設計意図（コメントに書く必要はないが、実装を変えないこと）:

- **判定の基準は `bucket.last_time`**（そのバケツに畳まれた quote の最大 broker 時刻）。
  開いているバケツは常に最新のバケツなので、これが broker 時刻の high-water mark になる
- **`bucket_start(tick.time) < bucket.start` を条件に含める**理由: 4h / 1d のようにバケツが
  30 分より広い足では、1 時間の逆行でも同じバケツに留まることがある。その場合は逆行として
  扱わず、既存の畳み込み経路（`start == bucket.start` → `_fold`）にそのまま乗せる。
  `_fold` は broker 時刻で open / close を決めるので、逆行した quote が close を奪わない
- 逆行と判定した tick は、確定した Bar には**畳み込まない**。それは 1 つ前のローソク足に属する
  quote であり、新しいバケツの最初の quote になる
- 閾値を足の長さでスケールさせない（1d 足で `max(30分, 1d)` にすると DST 逆行が検出されなくなる）

### 4-3. `BarBuilder` の docstring を更新する

クラス docstring の末尾（"...because broker timestamps are never converted into our own time."
の後）に 1 段落足す。**broker 時計が動いた瞬間だけは例外で、逆行を検出してバケツを畳み直す**こと、
繰り返される 1 時間ぶんの Bar は既存行と `start_at` が衝突して `ON CONFLICT DO NOTHING` で
捨てられること（それが正しい: 先に書かれた行が「その時点で知り得た姿」である）を書く。
ADR-032 を参照する。

## 5. 実装 2: ポーリング欠損の穴埋め（issue #33）

`src/trading/data/market/collector.py`

### 5-1. モジュール定数を追加する

`BACKFILL_WINDOW` の隣:

```python
# How wide a hole between two polled quotes is still closed from the tick
# history. A burst the poll loop undersampled leaves milliseconds to seconds
# behind; anything wider is a market closure or a collector outage, and
# repairing those is the scheduled backfill's job, not the poll loop's.
POLL_GAP_MAX = timedelta(seconds=60)
```

### 5-2. `poll_once` を書き換える

方針:

1. `symbol_info_tick` を呼ぶ。`None` なら今までどおり `MT5ConnectionError` を投げる
2. `received_at = self._clock.now()` を 1 回だけ取り、polled tick を作る
3. `(tick.time, tick.bid, tick.ask)` が前回と同じなら今までどおり `0` を返す（変化なし）
4. 前回の quote があり、`0 < tick.time - previous_time <= POLL_GAP_MAX` のときだけ
   `copy_ticks_range(symbol, previous_time, tick.time, COPY_TICKS_ALL)` を呼び、
   返った行を `tick_from_row(row, symbol, received_at)` で Tick にする
   - `copy_ticks_range` が `None` を返したら `MT5ConnectionError` を投げる
     （`backfill` と同じ扱い。取得失敗を「気配値なし」と読ませない）
5. 穴埋めで得た Tick 群 + polled tick を、`(time, bid, ask)` をキーに**重複を落として**から
   broker 時刻順（同値は取得順）に並べ、1 回の `self._write(...)` で書く
   - 落とすのは (a) 前回の quote と同じ `(time, bid, ask)` を持つ行（既に格納済み）、
     (b) polled tick と同じ `(time, bid, ask)` を持つ行。**range の端が inclusive か
     exclusive かに実装が依存しないようにする**ため、範囲の絞り込みではなく重複除去で行う
   - DB 側の `ON CONFLICT (symbol, event_time, bid, ask) DO NOTHING` があるので
     重複は最終的には吸収されるが、`insert_many` の戻り値（実際に書けた行数）を
     poll_once の戻り値として意味のあるものに保つために手前で落とす
6. 前回 quote が無い（プロセスの最初のポーリング）ときは穴埋めしない。どこまで遡るかの根拠が無い

制約:

- `received_at` は穴埋め分も polled tick と同じ `received_at` にする。実際にこの
  ポーリングで届いたのだから、それが point-in-time として正しい
- `self._last_quote[symbol]` の更新は今までどおり polled tick の quote で行う
- MT5 呼び出しが増えるのは**新しい気配値が出たポーリングだけ**（変化なしのポーリングは
  手順 3 で早期 return するので追加コストゼロ）
- 補助関数を作るなら `TickCollector` の private メソッド 1 つに収める。モジュール
  レベルの新しい公開関数は作らない

### 5-3. モジュール docstring を更新する

冒頭の「Two paths, deliberately different in purpose」の箇条書きを直す。
現在は「polling series is never a complete tick record」と書いてあるが、
穴埋め後は「ポーリングは最新 1 本しか返さないので、2 回のポーリングの間に届いた気配値は
直後に tick history から埋める。埋められるのは `POLL_GAP_MAX` までの穴で、
市場休止やプロセス停止のような広い穴は今までどおり定期 backfill の仕事」に変える。
`copy_ticks_range` の行も、「後から完全な系列を作る」だけでなく「ポーリングの穴も埋める」
ことが分かる文面にする。

## 6. ADR-032 を追加する

`docs/adr/ADR-032-bar-bucket-clock-step.md`。**日本語**で書く
（直近の ADR-030 / ADR-031 は日本語。AGENTS.md も日本語優先）。見出し構成は
`ADR-031-exit-only-signal-through-session-gate.md` に合わせる
（`# ADR-032: <題>` → `**Status:** Accepted (2026-09-07)` → `## Context` →
`## Decision` → `## Consequences`）。

構成（`## Context` に「何が起きるか」、`## Decision` に採用した規則、
`## Consequences` に副作用。下の材料をその 3 節へ割り付ける）:

- **Decision**: `BarBuilder` は broker 時計の逆行（開いているバケツの最大 broker 時刻より
  `CLOCK_STEP_BACK` 以上前で、かつ別のバケツに属する quote）を、遅着ではなく
  「サーバーの時計が動いた」と読む。開いているバケツを確定して publish し、新しい位置で
  バケツを開き直す。閾値より小さい逆行は今までどおり straggler として捨てる
- **Rationale**:
  - ADR-005 は恒常オフセットを扱えるがオフセットが変わる瞬間を扱えない。逆行中は
    畳み込みも確定も成立せず、約 1 時間ぶんの Bar が丸ごと落ちる
  - 単一の tick では逆行と遅着を区別できない。区別できるのは幅だけ:
    DST は 1 時間ちょうど、フィード内の並び替えは秒単位。30 分はその間に置いた線
  - 経過時間による staleness guard（もう 1 つの候補）は 2 つの時計を混ぜずに済むが、
    「バーをいつ諦めるか」を時計の進み方に依存させるため、tick が来ない静かな時間帯でも
    バーを確定させてしまう。逆行の検出は逆行のときにだけ発火する
- **Consequences**:
  - 逆行後に繰り返される 1 時間ぶんの Bar は、既存行と `(symbol, timeframe, start_at)` が
    衝突して `ON CONFLICT DO NOTHING` で捨てられる。先に書かれた行が「その時点で
    知り得た姿」なので、これは正しい。tick 系列には両方残るので replay は影響を受けない
  - live の `bar_service` は最後に書いた Bar の終端から読み直すので、逆行した 1 時間の
    tick はそもそも読まれない。ここで閉じるのは、known-time 順に tick を配る
    replay engine と、逆行を含む系列を畳むあらゆる経路
  - 1 分足に対して 30 分以上遅れて届いた 1 本の quote は逆行と誤読される。その場合
    ローソク足 1 本が本来より早く確定するが、既に publish 済みのバーは書き換わらない
  - **開いているバケツは 1 つのまま**（issue #12）。先行 quote は今までどおり
    直前のバケツを確定させて自分のバケツを開く。その後に届いた旧バケツ宛ての quote は
    捨てられる。これを直すには複数バケツと複数 Bar の戻り値が要り、`BarBuilder` の
    単純さと引き合わない

## 7. テスト

### 7-1. `tests/unit/test_bar_builder.py`

既存テストは**一切緩めない・書き換えない**。以下を追加する。
共通の注意: `Tick.known_time` は `received_at` が None のとき `time` にフォールバックするので、
**逆行を扱うテストでは `received_at` を必ず明示する**（自分の時計は逆行しない）。

1. `test_a_broker_clock_that_steps_back_keeps_publishing_bars`
   - 1m 足。合成 tick 列を次の形で作る:
     - 前半: broker 時刻 `at(seconds=0)`, `at(seconds=30)`, `at(minutes=1)`,
       `at(minutes=1, seconds=30)`（`received_at` は同じ刻みで単調増加）
     - 後半: DST 終了を模して broker 時刻を **1 時間戻す**。
       `at(minutes=2) - timedelta(hours=1)` から 30 秒刻みで 10 本
       （`received_at` は前半から続けて単調増加させる）
   - この列で期待される publish（実装前に手で追った結果。実装後に食い違ったら
     **実装ではなくこの期待値を疑う前にまず手で追い直す**）:
     - `T0` の Bar は broker 時刻 `at(minutes=1)` の tick が確定させる（`tick_volume == 2`）
     - `at(minutes=1)` の Bar は**逆行 tick が確定させる**（`tick_volume == 2`）
     - その後、逆行後の系列が 1 分ごとに Bar を出す（最後の未確定バケツを除く）
   - assert する内容:
     - publish された Bar の `start` の列を**完全一致で** assert する
       （「9〜10 本」のような曖昧な条件にしない）
     - 逆行後の最初の Bar の `open` が逆行後の最初の quote の bid であること
       （逆行 tick が捨てられていない）
     - すべての Bar の `known_at` が単調非減少であること（自分の時計は戻らない）

2. `test_a_quote_less_than_the_step_threshold_behind_is_still_a_straggler`
   - 1m 足。`at(minutes=40)` のバケツを開いた状態で `at(minutes=20)` の quote（20 分遅れ、
     閾値 30 分未満）を渡し、`None` が返ること・開いているバケツが確定していないことを assert する
   - その後 `at(minutes=41)` の quote で publish された Bar が、遅着 quote を含まないこと
     （`tick_volume`・`high`）を assert する

3. `test_a_step_back_inside_the_open_bucket_only_folds`
   - 4h 足。バケツ `[04:00, 08:00)` を broker 時刻 06:00 の quote で開き、1 時間逆行した
     05:00 の quote を渡す。バケツは 4 時間幅なので同じバケツに留まる → `None` が返り、
     Bar は確定しない。05:00 の quote は畳まれる（`tick_volume == 2`）が、broker 時刻が
     06:00 より前なので `close` を奪わないことを assert する

4. `test_a_leading_quote_under_clock_skew_seeds_the_next_bar` （issue #12 の回帰テスト）
   - broker 時計が受信時計より進んでいる状況を合成する。`time` は +3h、`received_at` は
     素の時刻。ある quote だけ `received_at` を前倒しして「バケツ終端に達したと分かる前に
     届いた先行 quote」を作る
   - その先行 quote が捨てられておらず、**次のバケツの Bar の open / high / low に
     反映されている**ことを assert する
   - 同時に、確定した前のバケツの Bar がその先行 quote の価格を含まないことも assert する

5. `test_a_skewed_series_loses_no_bar_and_no_extreme` （issue #12 の回帰テスト）
   - +3h skew の下で 1m 足を 5 分ぶん、1 分あたり複数 quote（極値を持つもの・持たないもの）で
     合成し、publish された Bar 列が「バケツごとに 1 本」「各 Bar の high / low が
     そのバケツの quote 群の最大 / 最小と一致」「`tick_volume` の合計が入力 quote 数と
     一致（最後の未確定バケツを除く）」ことを assert する

### 7-2. `tests/unit/test_tick_collector.py`

既存の `FakeMT5` / `FakeTickRepository` / `make_collector` を使う（`FakeMT5.copy_ticks_range` は
`date_from <= t < date_to` で絞る実装。`FakeMT5.__init__` の `range_rows=None` は
「取得失敗（`None` を返す）」を意味する）。`FakeTickRepository` は重複を落とさないので、
「格納された tick が何本か」の assert は実装側の重複除去を直接検証することになる。

受信時刻を進めたい場合は `tests.support.FixedClock` の `advance(**kwargs)` を使う
（`FixedClock(T0)` → `clock.advance(seconds=1)`）。

1. `test_quotes_missed_between_two_polls_are_filled_from_the_tick_history`
   - `symbol_info_tick` は急変時のバースト 9 本のうち 1 本目と 9 本目だけを返し、
     `copy_ticks_range` は 9 本すべてを持つ、という FakeMT5 を組む
   - 2 回ポーリングして、格納された tick が 9 本すべてであること・broker 時刻順であること・
     `received_at` が 2 回目のポーリング時刻であること（穴埋め分）を assert する

2. `test_a_burst_that_polling_samples_still_yields_the_full_high_and_low`
   （issue #33 が求める「極値落ちが起きない」検証）
   - 上と同じ形のバーストを、極値（最高値・最安値）が**ポーリングで拾われない位置**に
     置いて組む。格納された tick を `BarBuilder("USDJPY", "1m")` に流し込み、
     確定した Bar の `high` / `low` がバースト全体の最大 / 最小と一致することを assert する
   - 対照として、穴埋め前の挙動（polled tick だけを畳む）では極値が落ちることを
     同じテスト内で示す必要はない（テストを二重にしない）

3. `test_an_unchanged_quote_costs_no_tick_history_call`
   - 同じ quote を返し続ける FakeMT5 で 3 回ポーリングし、`range_calls` が空であること

4. `test_the_first_poll_of_a_process_fills_no_gap`
   - 1 回目のポーリングで `range_calls` が空であること（どこまで遡るかの根拠が無い）

5. `test_a_gap_wider_than_the_bound_is_left_to_backfill`
   - 前回 quote から 10 分後の quote を返し、`range_calls` が空であること・
     polled tick だけが格納されることを assert する（週末明けを想定）

6. `test_a_failed_tick_history_fetch_is_not_read_as_an_empty_burst`
   - 穴埋めの範囲取得が `None` を返す FakeMT5 で `MT5ConnectionError` が上がることを assert する
