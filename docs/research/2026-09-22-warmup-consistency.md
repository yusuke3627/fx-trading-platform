# 初期履歴による指標・売買判断の差を検査する

Issue #217。`monetary_policy_convergence` の研究リプレイは、日足EMAの期間50を初期履歴の本数としていた。一方、`IndicatorService` は通常200本を読み、渡された系列の先頭で初期化してEMAを計算する。同じ評価時点でも、50本程度で始めた値と200本を使った値が異なり、LONGのトレンド条件を反転させ得る。

戦略版 `0.2.1` では、trend時間足のEMAとtrigger時間足のATRについて、通常読む窓を満たすよう初期履歴を算出する。既定の日足trendでは200営業日相当を既存の週末・休場余裕で暦日に換算し、282日前から読み始める。大きいATR期間、supportの参照幅、銘柄別パラメータや時間足変更も計算に反映する。売買条件、Risk、OMS、liveの取得処理は変更しない。

## 検査

```sh
env -u TRADING_DB_DSN .venv/bin/pytest -v tests/replay/test_warmup_consistency.py
```

登録済みの4戦略を対象に、宣言した初期履歴とその2倍を、同一の合成確定足・tick系列から切り出す。実際に読ませる履歴が異なることを確認し、同じ評価開始時刻から実指標と実戦略の`on_event`を実行する。各時間足のATR・EMAと、UUIDだけを除いたシグナル全体を照合する。各戦略でシグナルが発生する系列を使い、空列同士の一致だけで合格しない。

履歴不足の対照では、過去の高い価格から下落して直近60本が戻る日足を使う。従来の50本相当の初期履歴ではLONG、通常の200本を満たす履歴では見送りとなり、指標値と判断の両方の差を検出する。このケースは検査が不一致を見逃さないことを確かめるもので、実市場での発生率を表さない。

参考にしたのはFreqtradeの[recursive-analysis](https://www.freqtrade.io/en/stable/recursive-analysis/)の履歴長比較である。本体やコードは取り込まず、既存のPython実装を検査する。Freqtradeの最終行の指標差に加え、こちらでは評価時刻ごとのシグナルの差も比較する。

## 実データを測るときの条件

既存の`trading.backtest.research --warmup-days`で初期履歴を明示できる。既定の282日より短く指定すると、値が通常状態と異なる可能性は残る。初期履歴を延ばした実験では、価格・feature・swapの保存済み入力、評価期間、設定、コード、seedを固定して比較する。履歴が不足する期間でcoverage検査を緩めない。

ここで確認するのは合成確定足を使った初期化の回帰であり、tickからの足生成、時計ずれ、長期休場・欠測、実口座の保有状態、約定結果の一致を証明しない。足生成、初期履歴中の発注禁止、PITとShadow/Replayの整合は既存の各検査で扱う。既存の週末換算は休場日数の上限保証ではなく、実データの収集範囲と指標窓の充足は実測時にも確認が必要である。

この変更によって過去の収益性判定を昇格させない。修正前後を同じ戦略版として集計せず、必要な研究は新しい版と入力範囲で再測定する。
