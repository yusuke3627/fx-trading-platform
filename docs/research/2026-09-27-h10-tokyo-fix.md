## 設計ノートを実データに当てるときの決めごと

- **Plan の値**: ブートストラップの乱数の種は `20260929`。他の値（営業日と五十日の定義、時刻、価格の窓 60 秒、期間、ブートストラップの
  回数 10,000、区間の水準、棄却の閾値 0.5bp、コストの感応度の倍率 0 と 2、上下 1% の刈り込み、副の区間の 6 か月のブロック）は設計ノートのとおり
- **同じ時刻の tick**: 窓の中の最初の tick では、同じ時刻に並ぶもののうち先に出たもの（DB では `id` の小さいもの）を使う。10:00 の直前の
  最後の tick では、後に出たもの（DB では `id` の大きいもの）を使う。どちらも DB の読み方（`ORDER BY event_time, id` と
  `ORDER BY event_time DESC, id DESC`）と向きをそろえた。後者は副の論文の形だけに効く
- **区間が決まらない場合**: 抽出した月に事象が 1 つも無い回があれば、その区間は `null` とし、回数を記録する。主の区間は事象のある月だけを
  単位にするので、起きない。副の 6 か月のブロックでは、OANDA の確認の期間に tick の欠けの月があるので、理屈の上では起こり得る
- **論文の形のコスト**: 9:50 と 10:00 はスプレッドの半分ずつ、9:55 は売りと売り越しでスプレッドを丸ごと 1 回分払うとして、
  `(s_9:50 / 2 + s_9:55 + s_10:00 / 2) × 0.01 / P_9:50 × 10,000`（bp）とする。`s_10:00` は、10:00 の直前 60 秒の最後の気配のスプレッドの平均である
- **時刻の軸**: Dukascopy の tick の時刻は実 UTC である。研究用 DB の `event_time` は MT5 のサーバー時刻のラベル（ニューヨーク時刻 + 7 時間）なので、
  日本時間の時刻を実 UTC に直してから `known_to_broker_label` でラベルに写して読んだ

## 解釈

- **判定は事前に決めた規則どおり「判定不能」。** 主の判定期間の純利益 0.22bp は、0 とも、棄却の閾値 0.5bp とも区別できなかった。
  設計ノートの検出力の表では、本当の純利益が 0.3bp 前後なら判定不能が 4〜6 割出る。その範囲の結果である
- **仲値前のドル高そのものは、2014 年以降も残っていた。** コストを引く前の粗利は 0.79bp で、片側 95% 区間（0.43〜1.16bp）は 0 を含まない。
  五十日以外の日（0.51bp）より 0.28bp 大きく、仕組みが予言する向きである。ただし、見当付けの期間（2010〜2013 年）の 1.50bp からは約半分に
  減っている。設計ノートで「半分に減っていれば支持は 44〜70%」とした場合に近い
- **取り分の約 7 割は OANDA のスプレッドに消えた。** 9:30 と 9:52 のスプレッドの半分ずつ（0.57bp）を引くと、純利益は 0.22bp しか残らない。
  年に約 75 回の取引で、年率のシャープレシオは 0.28 にとどまる。H8・H9 ではスワップの上乗せが取り分を消したが、H10 ではスプレッドが消した
- **OANDA の実際の気配では 0.56bp だった**が、143 日しかなく区間は −0.59〜1.70bp と広い。2024 年以降は 1 ドル 150 円前後で、同じ pips の
  スプレッドが bp では小さい（0.45bp）ことも効いている
- **論文の形（9:50 買い → 9:55 売り越し → 10:00 買い戻し）は、粗利 2.47bp と、主の形の 3 倍あった。** 9:55 の前後の値動きは、論文の標本の後も
  強く残っている。OANDA が 9:53〜9:55 に広げるスプレッドを払っても純利益は 0.48bp で、月単位の区間の下限はほぼ 0（0.004bp）だった。
  ただしこれは、設計の段階で選ばなかった形の副の報告で、判定には使わない。見当付けの期間（1 ドル 80 円前後でコストが bp で大きかった）では
  純利益が −0.63bp だった。この形を支持の証拠とは読まない。新しく測るなら、2026-09 以降の未使用のデータで、あらためて事前登録が要る
- 事前に決めた扱いに従い、判定不能なので運用には進まない。区間を記録し、仲値前の取引で言えることの範囲として残す
