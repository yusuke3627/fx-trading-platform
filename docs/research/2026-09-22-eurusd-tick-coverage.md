# EURUSD 歴史 tick の取り込みとカバレッジ（2024-08〜2026-09）

- 測定日: 2026-09-22（2026-09-24 に集計区間を broker ラベル軸へ直して再測定）
- 対象: `market_ticks` の EURUSD
- 取り込み経路: [dukascopy.py](../../src/trading/data/market/dukascopy.py)
- 実行ホスト: 執行 VPS（market tick を持つ DB はこちらだけ）
- 結論: 取引時間 13,320 時間に対し、**配信元から取得できなかった時間帯は 16 時間（0.12%）**

## 目的

USD/JPY 以外を shadow・backtest の対象へ加えるには、実収集を始めた 2026-09-17 より前の tick が要る。
Dukascopy の無償歴史 tick で EURUSD の 2 年分を埋め、**どれだけ埋まったかを DB 側で実測して記録する**。
取り込みコマンドは既存のものをそのまま使い、本ノートはコードを変更しない。

範囲は 2024-08-01〜2026-09-17（実 UTC）とした。開始日は USD/JPY の MT5 系列が始まる 2024-07-23 に
揃えた値で、複数ペアを同じ窓で比較できるようにするためである。終端は実収集の開始日で、重なる
時間帯は既存 tick があるため取り込み側が自動で飛ばす。

## 取り込みの経過

範囲を 2 つに分け、それぞれ初回と穴埋めを流した。穴埋めは同じコマンドの再実行で、既に tick が
ある時間帯は取りに行かない。

| run | 範囲（実 UTC） | 取り込み件数 | ログ上の失敗 |
| --- | --- | ---: | ---: |
| 初回 | 2025-09-01〜2026-09-17 | 18,021,665 | 430 |
| 初回 | 2024-08-01〜2025-09-01 | 26,337,203 | 421 |
| 穴埋め1 | 2025-09-01〜2026-09-17 | 833,687 | 106 |
| 穴埋め2 | 2025-09-01〜2026-09-17 | 31,161 | 116 |
| 穴埋め1 | 2024-08-01〜2025-09-01 | 1,271,768 | 140 |

合計 46,495,484 件。失敗の内訳は HTTP 503 が大半で、残りが接続タイムアウトとリセットである。
取り込み処理は 1 時間ファイルを取るたびに 0.1 秒（`REQUEST_INTERVAL_SECONDS`）待つだけなので、
通常時は最大で毎秒約 10 回、2 本並行ならその倍の要求を送る。要求頻度と失敗の関係は測っていないため、
失敗が配信元の都合によるものか、こちらの要求頻度によるものかは切り分けていない。

## カバレッジの測定

保存されている `event_time` は ADR-005 のブローカーラベル軸（New York + 7 時間）である。この軸では
取引週がラベル月曜 00:00 からラベル土曜 00:00 までの 5 日間にちょうど収まるので、**ラベル上の
月〜金を取引時間**とみなして 1 時間単位で突き合わせた。

取り込みの範囲は実 UTC で指定しているので、突き合わせる区間も同じ軸へ直す。取り込み側と同じ
`known_to_broker_label`（`broker_server_ahead_of_ny_hours: 7`）で変換すると、両端とも夏時間の日付なので
2024-08-01 00:00 UTC はラベル 2024-08-01 03:00、2026-09-17 00:00 UTC はラベル 2026-09-17 03:00 になる。

VPS の DB は実収集と共用なので、EURUSD の全行を読む集計は避け、期待する各時間に tick が 1 本でも
あるかを `market_ticks_quote_key`（`symbol, event_time, ...`）の索引で引く。

```sql
SET TIME ZONE 'UTC';
WITH expected AS (
  SELECT generate_series(timestamptz '2024-08-01 03:00:00+00',
    timestamptz '2026-09-17 03:00:00+00' - interval '1 hour', interval '1 hour') AS h
),
checked AS (
  SELECT h, EXISTS (
    SELECT 1 FROM market_ticks
    WHERE symbol = 'EURUSD' AND event_time >= h AND event_time < h + interval '1 hour'
  ) AS present
  FROM expected
  WHERE extract(isodow FROM h) BETWEEN 1 AND 5
)
SELECT count(*) AS trading_hours,
       count(*) FILTER (WHERE NOT present) AS missing
FROM checked;
```

ラベル上の月〜金 13,320 時間のうち、tick が 1 本も無いのは 94 時間だった。内訳は次のとおり。

| 区分 | 時間 | 中身 |
| --- | ---: | --- |
| 市場の休場 | 78 | 元日 24×2（2025-01-01・2026-01-01）、クリスマス 14×2（2024-12-25・2025-12-25）、聖金曜日 2（2025-04-18） |
| **取得失敗** | **16** | 単発の 1 時間のみ（下記）。2 時間以上続く欠けは無い |

取得失敗の 16 時間（ラベル時刻）は次のとおり。

- 2024: 08-07 6 時、08-08 2 時、09-10 10 時、09-20 20 時、10-01 1 時、10-30 8 時、10-31 7 時、11-06 23 時、11-21 11 時、11-28 7 時
- 2025: 02-21 1 時、02-28 14 時、03-28 13 時、04-29 23 時、06-12 1 時、07-14 10 時

つまり実際に取りこぼしたのは **16 時間（取引時間の 0.12%）** で、残りは市場が開いていない時間帯である。
上の SQL は祝祭日を持たないので、欠測を数えたあとに日付を並べて分類する必要がある。
取得失敗の各時刻は `checked` から `WHERE NOT present` の行を並べれば得られる。

最初の測定（2026-09-22）は区間の両端を実 UTC のまま比較しており、要求範囲の外にあるラベル
2024-08-01 00:00〜02:59 の 3 時間を欠測に数え、要求範囲の内側にあるラベル 2026-09-17 00:00〜02:59 を
検査していなかった。区間を直した再測定で前者は消え、後者の 3 時間には tick があった。

ラベル上の土日に tick が入っている時間帯は **0 件**である。ブローカーラベルへの変換が取引週の
境界と一致していることの確認になる。

## 測定で踏んだ罠

### セッションのタイムゾーンで曜日がずれる

最初の測定は平日の欠測を 1,368 時間（10.3%）と出した。原因は `extract(isodow FROM ...)` が
**セッションのタイムゾーンへ変換してから**曜日を求めることである。VPS の psql は Asia/Tokyo で
動くため、ブローカーラベル軸の日曜 15:00〜23:59 が月曜として数えられ、取引していない 9 時間が
欠測に化けていた。逆にラベル金曜 15:00〜23:59 は土曜として集計から落ちていた。

`SET TIME ZONE 'UTC'` を先に置けば解消する。ブローカーラベルは tzinfo=UTC で保存される値なので、
**この軸を扱う集計は必ず UTC セッションで行う**。

### ログの失敗回数はカバレッジの代理にならない

全 run のログは合計 1,213 件の失敗を記録しているが、実際に取りこぼした時間帯は 16 だった。
75 倍の開きがある。

- 配信元の障害とみなして待避したあと同じ時間帯を再試行するため、1 つの時間帯が複数回計上される
- 休場でもともと tick が存在しない時間帯の取得失敗も同じ行で記録される
- 後続の穴埋めで成功した時間帯も、前の run のログには失敗として残り続ける

取り込みの途中経過を眺めるにはログでよいが、**どれだけ埋まったかの判断には必ず DB を突き合わせる**。
本作業中、ログの失敗件数が横ばいなのを見て「これ以上は埋まらない」と誤って見積もった。実際には
穴埋めのたびに大きく減っていた。

## 打ち切りの基準

穴埋めを流す前に「取引時間に対する欠測が 1% を切ったら打ち切る」と決めて実行し、0.71%（取得失敗
だけなら 0.12%）で基準を満たしたため追加の実行はしない。

残る 16 時間は 2024-08〜2025-07 に散らばった単発の 1 時間だが、影響は tick 単位の約定シミュレーションに限らない。
`BarBuilder` は tick が来たときにしかバケツを開かず、tick のない時間を補完しない。そのため欠けた時間の
1 時間足は作られず、その時間を含む 4 時間足・日足などは欠けた時間の高値・安値を含まない不完全な足に
なる。**バーを使う指標・シグナル・約定結果も変わりうる。** 欠けが短いことを安全の根拠にせず、この
16 時間を含む期間を検証するときは上の SQL で欠測を確かめ、tick 単位とバー単位の両方で影響を受けうる
ものとして扱うこと。

## 範囲外

- USD/JPY の Dukascopy 系列（2022-01-03〜2024-07-23）は本測定の対象外
- GBP/USD・GBP/JPY は同じ手順・同じ範囲で取り込みを始めたが、2026-09-22 の VPS の再起動で止まった
  （GBP/USD は 2024-08-16 まで）。VPS のディスクを増設するまで再開しない（#57）
- 欠測時間帯を別の配信元で補うことは検討していない。同一期間での MT5 系列との混在を
  取り込み側が禁じており、第三の系列を混ぜれば同じ問題が起きる
