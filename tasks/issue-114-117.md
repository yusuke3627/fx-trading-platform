## 要件（issue 本文の転記）

### #117 OMS claim: `save_state` の CAS に claim 世代を含める（二重送信の窓を塞ぐ）

`PostgresCommandRepository.save_state` の compare-and-set は `id` と `state` しか
比較していない。

```sql
UPDATE execution_commands
SET state = ..., quantity = ..., claimed_by = ..., claimed_at = ..., claim_expires_at = ...
WHERE id = %(id)s AND state = %(expected_state)s
```

このため次の競合が通る:

1. worker A が row を claim する（`state=CLAIMED`, `claimed_by=A`, lease T まで）
2. A が queue で fresh select と revalidation をしている間に lease T を過ぎる
3. recovery sweep が `CLAIMED -> READY` へ戻し、worker B が再 claim する
   （`state=CLAIMED`, `claimed_by=B`）
4. A が `save_state(command, expected_state=CLAIMED)` を呼ぶ。row は CLAIMED なので
   CAS が通り、A の古い評価結果で `SUBMITTING` になり `claimed_by` が A へ上書きされる

結果、期限切れの fresh select と risk 評価に基づく送信が成立し、B と合わせて同じ論理注文を
2 回送りうる。

issue が挙げていた注意点（**実装時に必ず踏まえること**）:

- 単純に CAS へ `claimed_by` を足すと回収パスが壊れる。`state_machine.transition` は
  `CLAIMED -> READY` で `claimed_by` / `claimed_at` / `claim_expires_at` を None にするため、
  sweep が返す command をそのまま `save_state(expected_state=CLAIMED)` に渡すと CAS が
  「row の claimed_by = NULL」を要求して必ず 0 行になる
- 呼び出し側（worker ループ・recovery sweep）は M6 で未実装。**誰も設定しない引数を足さない**

issue の対応方針案のうち **案 2（SQL 側で条件付きにする）を採用する**。

### #116 OMS rate limiter: 複数 worker 間で送信窓を共有する（または単一 dispatcher を保証する）

`RateLimiter` の送信履歴はインスタンス内の `deque` にしかない。

```python
self._symbol_requests: dict[str, deque[datetime]] = {}
self._market_entries: deque[datetime] = deque()
```

`PostgresCommandRepository.claim_next` は claim lease による複数 worker / 複数プロセスの
同時稼働を明示的に想定している。その構成では worker ごとに独立した `ExecutionQueue` と
`RateLimiter` を持つため、各 worker が同じ symbol へ最大 5 件ずつ同時送信でき、broker 全体の
上限（同一 symbol 5 requests/sec、market new entry 1/sec）を超える。

issue の対応方針案のうち **案 1（単一 dispatcher を保証する）を採用する**。理由は
個人・自己資金運用で Windows 1 台という前提（AGENTS.md「プロジェクト概要」）に対して
共有ストレージ予約（案 2）は過剰で、ADR-030 の「DB schema は変更しない」とも衝突するため。
ただし「ADR に書くだけ」では保証にならないので、**PostgreSQL の session 単位 advisory lock で
実際に排他する**。

### #115 OMS queue: netting の縮小 delta を market entry / NEW_ENTRY として扱わない

`ExecutionQueue.dispatch` は rate limit の区分を command の action だけで決めている。

```python
market_entry = command.action in (PositionAction.OPEN, PositionAction.INCREASE)
```

NETTING 口座では `OMSService.command_for_netting()` が、例えば net short 80,000 を
short 60,000 へ縮小する LONG の OPEN intent から BUY 20,000 の command を作る
（`_command` が `action=intent.action` を設定するため action は OPEN のまま）。
実体はリスク縮小だが、queue では market new entry として 1/sec の窓を消費し、
`priority_for()` でも NEW_ENTRY になって真の新規注文と同列に並ぶ。結果、別 symbol の
新規 entry の直後に来たリスク縮小注文が最大 1 秒待たされる。

issue の対応方針案のうち **案 3（NETTING では縮小 delta を REDUCE / CLOSE action の command
として作る）を採用する**。案 1・2 は producer 側の契約追加または DB 列追加を伴うが、
`command_for_netting` は `current_net` と `desired_net` を両方持っているので、
exposure の増減はその場で判別できる。

### #114 OMS queue の signal 失効時刻（`expires_at`）を再 claim 後に復元できるようにする

`ExecutionQueue.enqueue` の `expires_at`（signal の失効時刻）は `QueuedCommand` の
in-memory 表現にしか保持されておらず、`ExecutionCommand` にも `execution_commands`
テーブルにも保存されていない。このためプロセス停止や claim lease 回収の後に DB から
command を再 claim した worker は元の期限を復元できず、`expires_at=None` で enqueue すると
既に失効した signal を送信できてしまう。

issue の対応方針案のうち **案 1（`execution_commands` に失効時刻の列を追加し、claim 時に
復元して enqueue する）を採用する**。案 2（intent 側に持たせて辿る）は portfolio 層と
`position_intents` への波及が大きく、案 3（queue から期限判定を外す）は queue 待機中の
失効を検出できなくなるため ADR-030 の送信直前チェックを弱める。

### D1（#117）: claim を保持したまま書く `save_state` は claim 世代も CAS に含める

`save_state` に引数を足さず、**書き込む command が claim を保持しているか**で SQL の
WHERE を切り替える:

- `command.claimed_by is not None`（＝ claim を保持したままの書き込み。`SUBMITTING` /
  `CANCELLED` / `EXPIRED` / `UNKNOWN` への遷移）
  → `WHERE id = ... AND state = ... AND claimed_by IS NOT DISTINCT FROM ...
     AND claim_expires_at IS NOT DISTINCT FROM ...`
- `command.claimed_by is None`（＝ claim を手放す書き込み。recovery sweep の
  `CLAIMED -> READY`。`transition` が claim 列を None にする）
  → 従来どおり `WHERE id = ... AND state = ...`

`SET` 節が書く `claimed_by` / `claim_expires_at` は、claim 保持時には「観測した値」と
同一なので、**WHERE でも同じプレースホルダを使い回す**（別引数を足さない）。
NULL 比較を確実にするため `=` ではなく `IS NOT DISTINCT FROM` を使う。

これで #117 のシナリオは 4 で 0 行 →`StaleCommandStateError` になり、A の送信は成立しない。
issue が案 2 の残課題として挙げた「古い sweep が新しい claim を解放する競合」は残るが、
その場合も新 worker 自身の `save_state` が弾かれるので二重送信にはならない。

### D2（#116）: 送信は単一 dispatcher に限定し、PostgreSQL advisory lock で排他する

- `oms/dispatch_lock.py` に `DispatchLock` Protocol（`held() -> bool`）と
  `DispatcherNotHeldError` を置く
- `ExecutionQueue.__init__` が `dispatch_lock` を必須キーワードで受け取り、
  `dispatch()` の先頭で `held()` が False なら `DispatcherNotHeldError` を送出する
  （既定値を与えない。既定を与えると保証を黙って迂回できる）
- `storage/postgres.py` に `PostgresDispatchLock` を追加。`pg_try_advisory_lock` は
  session 単位なので、接続が生きている間だけ保持され、プロセス停止で自動解放される
  （`pg_advisory_xact_lock` と違い rollback では解放されない点も、worker が長い
  トランザクションを持たない本構成に合う）。**`storage` から `oms` を import しない**
  ── Protocol は構造的部分型なので、`PostgresDispatchLock` は `DispatchLock` を
  継承も import もせず、`held()` / `acquire()` を持つだけでよい

`held()` は round trip を避けてローカルの取得フラグと `conn.closed` だけを見る
（接続断は運用上ふつうに起きる事象で、その時に他プロセスがロックを取れてしまうため
`closed` の確認は防御的分岐ではない）。

### D3（#115）: NETTING の command の action / direction は exposure の増減で決める

`command_for_netting` が、`current_net` と（zero-cross clamp 後の）結果 net から分類する:

| 条件 | action | direction |
| --- | --- | --- |
| 結果 net == 0 かつ current_net != 0 | `CLOSE` | current_net の符号 |
| `abs(結果 net) < abs(current_net)` | `REDUCE` | current_net の符号 |
| それ以外 | `intent.action` | `intent.direction` |

`side` は従来どおり delta の符号から決める。上表の direction / action の組は
`execution_side(direction, action)` と必ず一致する（テストで固定する）。
`idempotency_key` は `intent.action` を使っているので**変わらない**。

これにより `priority_for` は CLOSE_REDUCE を返し、`dispatch` の `market_entry` 判定は
False になる。queue 側のコードは変更不要。

### D4（#114）: signal 失効時刻は `ExecutionCommand` が持ち、DB に永続化する

- `ExecutionCommand.expires_at: datetime | None = None` を追加
- migration `0009_execution_command_expires_at.sql` で
  `execution_commands.expires_at TIMESTAMPTZ` を追加（**使ってよい連番は 0009 のみ**）
- `PostgresCommandRepository.insert` が書き、`_row_to_command` が読む。
  `save_state` は書かない（失効時刻は command 生成後に変わらない）
- `OMSService` の 3 つの builder（`command_for_netting` / `command_for_entry` /
  `command_for_hedging_exit`）が `expires_at` を受け取り `_command` が詰める
- **`ExecutionQueue.enqueue` の `expires_at` 引数と `QueuedCommand.expires_at`
  フィールドを削除**し、`dispatch` は `entry.command.expires_at` を読む。
  in-memory とのニ重管理をやめることが今回のバグの根治にあたる

## テスト方針

pytest。`tests/unit` に各 issue 対応のテストを足す。DB の CAS と advisory lock は
in-memory の fake では観測できないので `tests/integration` に足す
（`tests/integration/test_command_repository.py` の docstring が既にその方針を書いている）。

### #117（D1）— `tests/integration/test_command_repository.py`

- `test_a_write_from_a_worker_whose_claim_was_taken_over_is_refused`:
  A が claim → sweep が READY へ戻す → B が再 claim → A の `save_state(SUBMITTING,
  expected_state=CLAIMED)` が `StaleCommandStateError` になり、row は B の claim のまま
- `test_releasing_an_expired_claim_still_writes`:
  claim 保持者の lease 切れ → `transition(CLAIMED -> READY)` で claim 列が None の
  command を `save_state(expected_state=CLAIMED)` → 成功し `claimed_by` が NULL になる
  （issue が指摘した「回収パスが壊れる」問題が起きていないことの固定）

### #116（D2）— `tests/unit/test_oms_queue.py` + `tests/integration/test_command_repository.py`

- unit: `test_dispatch_requires_the_single_dispatcher_lock` — `held()` が False の
  lock を渡した queue の `dispatch()` が `DispatcherNotHeldError`。entry は queue に残る
- integration: `test_only_one_process_holds_the_dispatch_lock` — 別接続の 2 つの
  `PostgresDispatchLock` で 1 つ目 `acquire()` が True、2 つ目が False。
  1 つ目の接続を閉じると 2 つ目が取れる

### #115（D3）— `tests/unit/test_netting_and_oms.py` + `tests/unit/test_oms_queue.py`

- `test_netting_shrink_delta_is_a_reduce_command`:
  net -80,000 → -60,000 を LONG の OPEN intent から作ると
  `action is REDUCE` / `direction is SHORT` / `side is BUY` / quantity 20,000
- `test_netting_flatten_delta_is_a_close_command`: net -80,000 → 0 で `action is CLOSE`
- `test_netting_zero_cross_flatten_is_a_close_command`:
  既存 `test_netting_zero_cross_flattens_only` の +1000 → -1000 で `action is CLOSE`、
  `direction is LONG`、side SELL
- `test_netting_growing_delta_keeps_the_intent_action`:
  net -80,000 → -110,000 は `action is OPEN`（intent のまま）
- `test_netting_command_side_matches_action_and_direction`:
  上記 4 ケースで `execution_side(command.direction, command.action) == command.side`
- queue 側 `test_netting_shrink_does_not_consume_the_market_entry_window`:
  REDUCE の netting command（ticket なし）と別 symbol の OPEN を並べ、OPEN 送信直後でも
  REDUCE が同じ 1 秒窓で送れる

### #114（D4）— `tests/unit/test_oms_queue.py` + `tests/integration/test_command_repository.py`

- `test_expiry_is_restored_from_the_reclaimed_command`:
  `expires_at` を持つ command を（enqueue に期限を渡さずに）enqueue し、時刻を進めると
  `DispatchOutcome.EXPIRED` になる
- `test_oms_command_carries_the_signal_expiry`（`test_netting_and_oms.py`）:

```bash
createdb fx_itest_114
for f in migrations/*.sql; do psql "postgresql:///fx_itest_114" -v ON_ERROR_STOP=1 -f "$f"; done
TRADING_DB_DSN="postgresql:///fx_itest_114" .venv/bin/pytest tests/integration
```

## 規約の転記（`.claude/rules/*.md` 由来。Codex が読むのは AGENTS.md まで）

- コード変更は必ずこの worktree 内で行う。メインリポジトリ（main）で編集しない
- 構造把握は `rg`（`grep` は使わない）
- 金額・数量・価格は `Decimal`（indicator 計算のみ float 可）
- frozen model + `model_copy` のパターンを維持し、引数や共有オブジェクトを破壊しない
- 検証はシステム境界（設定・外部 API・Broker 応答）だけ。内部関数間に防御的分岐を足さない
- SQL はプレースホルダで組む（文字列連結しない）
- コメントは WHAT ではなく WHY。コミット文脈依存のコメント（「○○のために追加」）を書かない
- コミットは行わない（コミットと PR は Claude 側が担当する）
- enum 値を増やす変更は `migrations/0001_initial.sql` の CHECK 制約にも波及するが、
  本 PR は enum を増やさない
