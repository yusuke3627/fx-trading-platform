## 目的と判断の限界

主な意見のⅡ節から作る指標が、既存の `BOJ_POLICY_SHIFT_SCORE` と異なる情報を持つかを調べる。計画時点では、主な意見の約86件のうち H4 / H6 のリプレイ期間（2024-08-01〜2026-08-29）に入るのは17件だけで、market tick は VPS、政策イベントは Mac に分かれている。両方を持つDBがないため、収益の ablation や Data Upgrade Gate（期待増分価値 > 2 × データコスト）より先に、市場データを使わない冗長性の確認を置く。

この20件で同点群に差が出るかだけを判定する。冗長なら本計画の段階3をここで終了する。冗長でなければ段階3bの公表時刻前後のUSD/JPYイベントスタディへ進む根拠にするが、市場データとの統合は別作業とする。どちらの結果も収益性、将来の汎化性能、Gateの通過を証明しない。現在取得する過去文書の再分類を、当時の運用成績として扱わない。

## 分母と抽出の規則

`opinions.opinions_url` で原文URLを作り、段階1の `fetch_document` でPDFを取得・キャッシュし、段階2の `opinions.extract_pdf_text` で本文を抽出する。収集経路、採点、DB、ランタイムのfeature登録は変更しない。

前処理は独立した行のページ番号を除き、改行を含む空白を除去する。既知の見出し `Ⅱ．金融政策運営に関する意見` を一意に見つけ、次のローマ数字の節見出し（Ⅲ以降）または文書末尾までを切り出す。末尾の「以上」は除く。見出しの未知の表記、重複、空の意見、`⚫`以外の箇条書き、最初の`⚫`より前に本文がある場合は失敗とする。見出しの違いを測定中に自動推測して補わない。全20件でこの書式が成り立つかは未確認。

Ⅱ節の`⚫`で分割した意見数が分母である。LLMには正規化したⅡ節だけを送り、各`⚫`につき原文順に`stance`を1件返させる。

| stance | 抽出対象 |
|---|---|
| HIKE | 政策金利を引き上げる方向の明示（条件付きも含む） |
| HOLD | 政策金利を据え置く方向、利上げ・利下げを見送る明示 |
| CUT | 政策金利を引き下げる方向の明示（条件付きも含む） |
| UNSPECIFIED | 方向の明示がない、または一意に特定できない |

過去の決定への言及だけ、物価・賃金・市場金利、国債買入れ、一般的な正常化から政策金利の方向を推測させない。否定された方向を採らない。スコア・強度・confidence・根拠・要約・件数は抽出させない。出力配列の長さをLLMの意見数として機械計数と照合する。

APIはOpenAI Batchの `/v1/responses`、モデルは `gpt-5.6-luna` に固定する。段階1と同じく reasoning effort は medium、最大出力は4096 tokens、`store=false`。構造化出力はstrictなJSON Schemaで、外側の`opinions`と内側の`stance`をすべてrequired、各objectを`additionalProperties: false`とする。キーとSDKはCLI実行時だけ必要で、import・解析・テストには不要。

機械計数とLLMの意見数が異なる会合は抽出失敗とし、**両方の件数を表示し、LLM版の値をnullにする**。分母の選び直し、切り詰め、欠けた意見の補完をしない。キーワード版は機械抽出に成功していれば残す。

## 指標とキーワードの事前登録

研究版は `opinions_redundancy_screen_v1`、LLMの抽出結果を使う採点版は `opinions_stance_balance_v1`。

```text
opinions_stance_balance = (HIKEの意見数 − CUTの意見数) / Ⅱ節の全意見数
```

HOLDとUNSPECIFIEDも分母に含み、範囲は[−1, +1]。LLMに採点させず、整数の件数から分数で計算する。

キーワード版 `opinions_keyword_balance_v1` は同じ正規化済み意見と分母に対し、次の語の集合を固定して部分文字列で検索する。

- 引き上げ: `利上げ`、`金利引き上げ`、`金利を引き上げ`、`金利の引き上げ`、`金利引上げ`、`金利を引上げ`、`金利の引上げ`
- 引き下げ: `利下げ`、`金利引き下げ`、`金利を引き下げ`、`金利の引き下げ`、`金利引下げ`、`金利を引下げ`、`金利の引下げ`

```text
keyword_balance = (引き上げ語を含む意見数 − 引き下げ語を含む意見数) / Ⅱ節の全意見数
```

同じ方向の語が複数回出ても1意見につき1件。両方向が出れば両方に1件ずつ数えるため、分子への寄与は0となる。否定・過去への言及も語があれば数え、意味の解釈はしない。単なる物価・賃金の「引き上げ」を避けるため、利上げ・利下げ以外は金利を含む連語に限定する。活用・表記揺れを測定後に追加しない。

LLM版との比較では、全行の差、完全一致会合数、平均絶対差、最大絶対差、両者のSpearman順位相関、キーワード版の同点群の範囲と判定を出す。

**「ほぼ同じ」の基準も測定前に固定する。** 主判定と同じ 0.25 を単位に使う。全20件で `|LLM版 − キーワード版|` の最大が **0.25 未満**なら `keyword_sufficient`（キーワード版が LLM 版を同じ許容幅の中で再現している）、**0.25 以上の会合が1件でもあれば** `llm_differs` とする。同じ尺度を使うのは、二つ目の恣意的な数値を持ち込まないためで、0.25 が意見5件分に相当するという根拠は主判定と共通である。

この判定は副次で、主判定を置き換えない。`keyword_sufficient` なら、この feature に LLM は要らないことになり Gate のコスト側が変わる。`llm_differs` なら、どちらが正しいかはこの測定では決まらない（両者の正解ラベルが無い）ので、優劣ではなく差があるという事実だけを記録する。いずれも収益性の証明とは分ける。

## 主判定と失敗の扱い

1. 成否によらず20会合すべてを対応表に残し、既存スコア、機械計数、LLM意見数、両指標、差、失敗理由を出す。
2. 既存スコアの同点群ごとにLLM版の最小・最大・範囲（最大−最小）を出す。
3. **すべての同点群の範囲が0.25未満なら `redundant`（冗長）。いずれかが0.25以上なら `nonredundant`（冗長でない）。**
4. 1文書がおよそ20意見なら1件の方向の変化は0.05で、0.25は5件分に相当する。単独の判定揺れを超える差を求めるための事前登録値であり、結果を見て変更しない。判定は丸める前の分数で行う。
5. 主判定は全20件が成功した場合に確定する。失敗があれば `incomplete` とし、取得できた群の範囲は暫定値として成功数・予定数とともに残す。一部の群で0.25以上が観測されても、全20件の完了とは扱わない。
6. Spearmanは同点に平均順位を与えた記述統計に限る。成功件数を併記し、定数系列または2件未満ならnull。p値、有意性は出さない。

`custom_id`で結果を対応付け、出力順に依存しない。未知・重複IDはrunのエラー、欠落IDは該当会合の失敗とする。HTTP・Responses・message・Batchのどの段階も完了が必要で、Batchが `failed / expired / cancelled` の部分結果は成功に数えない。拒否・打ち切り・型不正も失敗とする。待機上限では暫定結果と再開コマンドを示す。

## 保存内容と費用

`tmp/opinions-signal/cache` にURLのSHA-256をキーとする原文キャッシュを置く。runごとに `manifest.json`（対象・原文SHA-256・正規化済み意見・プロンプト・語集合・版・閾値・単価・開始日時・YAMLハッシュ）、`input.jsonl`、`batch.json`、取得できた出力／エラーJSONL、`report.json` と `report.md` を保存する。manifestの会合は採点入力を含むため、resume時には現在のYAMLを読み直さない。登録した対象・モデル・プロンプト・語集合・版・閾値が現在のハーネスと異なる場合は再開を拒否する。新規runは既存ディレクトリへ上書きしない。原文取得や節の解析に失敗した会合の機械計数は0とせずnullにする。

費用はAPIが返すinput/output/cached tokensを使い、失敗した応答もusageがあれば加算する。usageのない送信対象件数を別記し、その場合の費用は確認できた分の小計とする。計算はDecimalを使う。

既定単価は段階1のローカル実装から引き継ぐBatch適用後の100万tokenあたり入力$0.10、キャッシュ入力$0.01、出力$0.60。272,000入力tokens超の入力・キャッシュ2倍、出力1.5倍の規則も段階1に合わせる。**今回は料金表へアクセスしておらず、実行時点の現行料金を確認した値ではない。** 必要なら実測前に下記3種類の単価をまとめて指定する。請求額ではなく、登録した単価による推定値である。

実データ測定は依頼者がネットワークを利用できる環境で行う。`OPENAI_API_KEY`を環境に設定したうえで、リポジトリルートから実行する。

# --input-price <Batch入力単価> --cached-input-price <Batchキャッシュ単価> \

### 測定前に直した抽出の不具合（run-1 → run-2）

最初の run（`tmp/opinions-signal/run-1`）は 20 件中 12 件が機械側の節分割で落ち、主判定 `incomplete`（成功 7 件）で終わった。LLM ではなく箇条書き記号の扱いが原因である。

この非対称性は当初の実装に入っておらず、成功した 17 件だけで `keyword_sufficient` を確定させていた（PR #196 のレビュー指摘）。同じ Batch 出力から判定を作り直して `incomplete` に改めた。**LLM 出力・プロンプト・閾値は変えていない。**

### 読み取れること

**主な意見から作る指標は、既存の `BOJ_POLICY_SHIFT_SCORE` と冗長ではない。** 既存スコアが同一と呼ぶ会合の間で、指標は意見 5 件分を超えて広がる。Spearman 0.090 は、既存スコアとの順位相関がほぼ無いことを示す。LLM 版は主判定が確定しないが、20 件で完結したキーワード版が `nonredundant` を出しており、両者は登録した許容幅の中で一致している。

**「この feature に LLM は要らない」は、今回の測定では確定していない。** 観測できた 17 件ではキーワード版が LLM 版を登録した許容幅の中で再現しているが、欠測 3 件を排除できないので比較判定は `incomplete` である。

確定はしないものの、方向としては機械抽出に有利な材料が揃っている。17 件すべてで差が閾値未満だったこと、失敗しているのが LLM 版だけであること、キーワード版だけが 20 件で判定を確定できたことの 3 つである。ここから言えるのは「機械抽出で足りる見込みがある」までで、Data Upgrade Gate のコスト側を書き換えるには欠測を埋めた測定が要る。

どちらが「正しい」かもこの測定では決まらない。両者に正解ラベルが無いためで、差があるという事実だけを記録する。

**この測定は収益性について何も言わない。** 言えるのは既存スコアと違う情報を持つことだけで、その情報が USD/JPY の予測に役立つかは段階3b の対象である。

### 設計上の反省

全 20 件の成功を主判定の確定条件にしたのは、非決定的な抽出器に対しては脆すぎた。1 件の数え違いで判定が永久に確定しなくなる。次に同種の事前登録を書くときは、再試行の方針か最小成功件数を測定前に決めておく。今回は事後に規則を足さず、`incomplete` のまま残す。

この脆さは 2 つの判定を同時に潰した。LLM 版の主判定だけでなく、LLM とキーワードの比較も欠測のせいで確定しない。決定論的なキーワード版だけが 20 件で判定を出せたという事実は、機械抽出に有利な材料ではあるが、それ自体は「LLM が不要である」ことの証明ではない。
