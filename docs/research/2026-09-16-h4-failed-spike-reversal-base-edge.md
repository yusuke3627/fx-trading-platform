# スパイク反転 scalp の基礎エッジ（H4 Model A）と判定

- 日付: 2026-09-16
- 対象: 仮説 H4「失敗したスパイクは数分で平均回帰する」。scalp 戦略 `failed_spike_reversal` の Model A（介入ゲートなし）
- 判定: **H4 棄却**（事前登録した判定規則の機械適用）。副判定（時間切れ決済の寄与）は**評価不能**
- 関連: issue #148（時間切れ決済の実装と事前登録）、issue #153、[ADR-036](../adr/ADR-036-horizon-exit.md)、[ADR-037](../adr/ADR-037-backtest-account-level-loss-halts.md)、研究ノート [`2026-09-06-shock-trigger-verdict.md`](2026-09-06-shock-trigger-verdict.md)、[`2026-09-10-h5-macro-confirmation-ablation.md`](2026-09-10-h5-macro-confirmation-ablation.md)

## 背景

H4 は「スパイクが失敗した直後は数分で平均回帰する」という仮説で、`failed_spike_reversal` はこれを 1 分足の scalp として実装したものである。Model A は介入ゲートを一切足さない素の形で、H2/H3 を棄却した時点（[`2026-09-06-shock-trigger-verdict.md`](2026-09-06-shock-trigger-verdict.md)）で次の測定対象に選んだ。

測定の前に決済構造を直す必要があった。H5 の測定では決済の 236 / 239 件が protection fill（ブローカー側の損切り）で、損切りにも利確にも当たらない建玉が銘柄あたり 1 本の枠を占め続け、25 か月中 13 か月で新規建玉が 1 件も通らなかった。この構造のまま H4 を測ると「スパイク反転で入って損切りまで持つ」戦略の成績になり、数分の平均回帰という主張そのものを測れない。そこで issue #148 で保有期限による時間切れ決済を戦略共通に追加し（[ADR-036](../adr/ADR-036-horizon-exit.md)）、その有無を 2 腕に分けて流した。

## 方法

同じ保存 tick・同じ期間・同じ seed で、`horizon_exit_enabled` を true / false にした 2 本の research リプレイを並列に流す。有効側は保有の経過時間が `expected_horizon_seconds`（この戦略では 300 秒）に達したら決済し、無効側は従来どおりブローカー側の損切りか反対方向のセットアップ信号でしか閉じない。

主判定の規則は実行前に issue #148 で固定した。有効側の腕の**約定あたり純損益**（執行コスト込み、carry は未値付け）の CI90 で決める。

| 条件 | 判定 |
|---|---|
| 有効側の約定が 10 件未満 | 判定不能（標本不足） |
| CI90 下限 > 0 | H4 支持 |
| CI90 上限 < 0 | H4 棄却 |
| それ以外 | 判定不能（差が検出できない） |

副判定（時間切れ決済そのものの寄与）は `ablation_compare.judge` の既存規則をそのまま当てる。上から順に評価する。

| 条件 | 判定 |
|---|---|
| 有効側の平均が高く、差の CI90 下限が 0 より大きい | 有効のまま維持（寄与あり） |
| 無効側の約定数が 2 倍以上で、平均が有効側以上 | 無効にする（絞るだけで質が上がらない） |
| どちらかの腕の約定が 10 件未満 | 判定不能（標本不足） |
| それ以外 | 判定不能（差が検出できない） |

CI90 は bootstrap（`BOOTSTRAP_SAMPLES` 回、seed 42）。部分決済は 1 エントリーを 1 標本に集約する。両腕の共通注文には安定注文キーで同じ執行ショックを割り当てるので、差に執行乱数の引き直しは混ざらない。research seed は 1 組（42）だけなので、H5 と同じく執行感応度は測っていない。

主判定に使う有効側の CI90 は、比較 CLI の `report` が `verify_comparable` で停止するため（「結果」節）、`ablation_compare.load_run` で有効側の run を読み、`ablation_compare.arm_summary`（seed 42）を単独で呼んで求めた。

この bootstrap は約定を 1 件ずつ復元抽出するので、各約定を独立で交換可能な標本として扱っている。同じ日や同じボラティリティ局面に約定が固まって損益に自己相関があると、有効標本数を過大に見積もり、区間は本来より狭くなる。日やセッションを単位にした block bootstrap は実装していないので、この影響の大きさは測っていない。判定は事前登録した規則どおりこの区間で行い、結果を見てから統計手法を差し替えることはしない。区間の幅について言えることは次のとおりである。平均 −8.1517 から上限 −7.2553 までの幅は 0.8964 で、上限が 0 に届くにはこの幅が 8 倍以上に広がる必要がある。block bootstrap でどれだけ広がるかは実際に計算するまで分からない（issue #164）。

`RiskEngine.evaluate` は全チェックを 1 回の評価で見て、失敗したコードをまとめて 1 つの棄却記録に書く。1 つの記録に複数のコードが載るので、コード別の合計は棄却レコード数を上回る。件数の単純合計を独立した理由の数として読まない。

建玉上限と最小ロット超過が両腕とも同数なのは偶然ではない。`_size_check` は許容数量を銘柄の数量上限（`max_units_per_symbol`）の残り枠でも絞ったうえでブローカー最小数量と比べる。USDJPY はこの数量上限も最小数量も 1,000 通貨なので、1,000 通貨の建玉が 1 本あると残り枠が 0 になり、リスク予算に余裕があっても最小ロット超過が立つ。時間切れ決済で建玉を解放すれば、建玉件数の枠と数量の残り枠は同時に空く。

## 判定

**H4 棄却。** 有効側の約定は 8,798 件で下限の 10 件を大きく超えており、標本不足には当たらない。約定あたり平均 −8.15 の CI90 は [−9.05, −7.26] で、上限が 0 を下回る。事前登録の規則の「CI90 上限 < 0」にそのまま該当する。

**副判定は評価不能。** 無効側が期末に建玉を 1 本抱えたままなので、比較 CLI は最初の検証段階で拒否し、`judge` まで到達していない。建玉が残ると損益が確定せず `trades.csv` が右側で打ち切られるため、腕どうしの比較が成立しない。検査は意図どおり働いている。

時間切れ決済の寄与を判定するには、終端の扱いを結果から独立させる必要がある。今回の run を見て「建玉が無かった時点」を `--to` に選ぶのは駄目である。終端が処置後の建玉寿命に依存するうえ、`research` は `--to` まで新規建玉を出し続けるので、終端を動かすと標本集合そのものが変わり、選択バイアスが入る。要るのは、評価終端を結果を見る前に固定し、その手前から新規建玉を止めて既存建玉だけを解消する、という終端処理である。現在の CLI にはこの指定が無い（`--from` / `--to` / `--warmup-days` だけで、新規建玉を打ち切る引数は無い）ので、副判定を成立させるにはハーネス側の変更が先に要る。

## 解釈

**1. この標本では粗損益が正で、その大きさがコストに届いていない。** 建玉は 1,000 通貨で USDJPY の pip は 0.01 円なので、1 pip は 10 円にあたる。有効側を 1 約定あたりに直すと、粗損益は +1.6376 円（0.164 pips）、執行コストは 9.789 円（0.979 pips）、差引が −8.152 円（0.815 pips）になる。ここで注意がいる。CI90 を出したのは純損益の分布に対してだけで、粗損益の側はエントリー単位に集計しておらず、信頼区間も検定も持っていない。言えるのは 8,798 件の標本平均が正だったというところまでで、母集団でもスパイク後の平均回帰が正の期待値を持つとは、この測定からは結論できない。確定しているのは純損益の側である。粗の点推定に対して執行コストが約 6 倍あり、その差が純損益の CI90 を 0 の左側に押し出している。執行コストのほとんどはスプレッドで、観測された値をそのまま払っており、こちらから縮められる量ではない。

**2. 標本を 2.5 倍にしても平均がほとんど動かなかった。** 打ち切られた 1 回目は 10 か月 3,556 件で −8.21、今回は 23 か月 8,798 件で −8.15 で、CI90 も重なっている。ただしこれを局面に対する頑健性として読んではいけない。1 回目の 10 か月（2024-08〜2025-05）は今回の 23 か月に丸ごと含まれており、2 つの測定は独立した局面ではない。加えて commit と設定が違うので `COMPARABLE_FIELDS` の意味でも比較可能ではない。重複しない期間に分けた損益はまだ見ていないので、この一致から言えるのは「同じ初期期間を含む 2 つの標本で平均が近かった」ところまでである。局面に対する頑健性を主張したいなら、期間を重複しないように分けて測り直す必要がある。

**3. 最大ドローダウン 72,608 は初期資金の 7.26% にあたる。** 実運用の高水準ドローダウン停止は 3.00% なので、仮に優位性があったとしてもこの戦略は運用の途中で止まる。今回期間全体を測れたのは、研究リプレイからこの停止を外したからである（[ADR-037](../adr/ADR-037-backtest-account-level-loss-halts.md)）。無効側の 40,782.95 も 4.08% で、同じく 3.00% を超えている。

**4. 無効側は比較の相手にならないが、それ自体が結果である。** 取引できたのは 25 か月中 11 か月、決済は 946 件すべてが protection fill、しかも期末に建玉を手放せていない。棄却 9,647 件が建玉上限で、損切りに当たらない建玉が銘柄あたり 1 本の枠を占め続けた。H5 で見た構造がそのまま再現している。粗損益も −26,697.50 と負で、1 約定あたりにすると約 −2.82 pips になる。時間切れ決済を入れた腕では粗が正、入れない腕では粗が負だが、**2 つの腕は約定集合そのものが違う**（8,798 件と 946 件で、月の分布も違う）ので、この符号の逆転を時間切れ決済の因果効果として読んではいけない。因果として読める形にするには、期末に建玉が残らない期間で測り直して比較 CLI を通す必要がある。

**5. 無効側の未値付けロールオーバーは 598 件ある。** この戦略は short のみで動かしている（long_side_enabled false）ため、現行の日米金利差ではロールオーバーの支払い側になる公算が高い。金利を値付けすれば無効側の実際の成績はここに出ている数字より悪くなる可能性がある。有効側は 300 秒で閉じるのでロールオーバーをまたいでおらず、未値付けは 0 件で、この不確実性は無い。

## 教訓

- **研究リプレイから口座水準の損失停止を外して、初めて期間全体を測れた。** 1 回目の測定は 25 か月のうち 10 か月で実質的に打ち切られていたが、当時はその事実を run の出力から読めなかった。停止が掛かったことは棄却コードを数えて初めて分かり、そこから [ADR-037](../adr/ADR-037-backtest-account-level-loss-halts.md) に至った。
- **到達範囲が `summary.json` に出るようになり、空白月と末尾の空白が run 成果物だけで読める。** 有効側 23 / 25 か月、無効側 11 / 25 か月という差は、`trades.csv` を後から数え直さなくても分かる。H5 のときは、入力条件が一致しているという理由で、標本が期間全体に散っていると書いてしまった。
- **比較 CLI の期末建玉チェックが機能した。** 時間切れ決済の無い腕は期末に建玉を手放せず、比較そのものが成立しない。損益が確定していない標本を平均に混ぜる前に止まった。
- **棄却コードは 1 回の評価で失敗した全コードが並ぶ。** 建玉上限と最小ロット超過が同数なのは、同じ建玉の占有から両方が出ているからで、独立した 2 つの理由ではない。件数の単純合計を理由の数として読まない。

## 次のステップ

- **H4 Model A は棄却する。** 介入ゲートを足す Model B / C は、全標本で粗 0.164 pips に対してコスト 0.979 pips という差を埋めなければ黒字にならない。ただしゲートは約定集合を絞るので、残る約定では粗も執行コストも変わる。差を埋める道は粗を上げる側だけではなく、スプレッドの狭い局面に寄せてコストを下げる側にもある。したがって測る前に示すべき事前根拠は「粗が 6 倍になる」ではなく、**ゲートを通った約定の条件付き純損益が正になる見込み**である。粗と執行コストの双方について、ゲートの条件とそれぞれの大きさを結びつける根拠を出せないなら測らない。
- **パラメータの探索はこのままでは行わない。** spike_atr_multiple や expected_horizon_seconds を動かす探索は、判定に使ったのと同じデータの上での探索になる。やるなら事前登録と期間分離が要る。
- **時間切れ決済の無い設計が枠を占め続ける問題は intraday の戦略にも同じ構造がある。** `post_event_failed_breakout` でも既定は off で、H5 の空白 11 か月はこれが原因だった。戦略ごとに測るより先に、枠の占有そのものを設計として扱うかを決める。
- **issue #157 の候補は利確が使えるようになった。** [ADR-038](../adr/ADR-038-strategy-take-profit.md) で戦略が利確距離を signal に載せられるようになったので、同じハーネスで測る。

## 再現

VPS で YAML 由来の collector（policy / intervention）を先に流し切り、`fx-macro` だけを止めたうえで（tick / bar / account / shadow のタスクは止めない）、2 腕を並列に流す。長時間の run は RDP を切断すると落ちるため、タスクスケジューラ経由で起動した。

```
python -m trading.backtest.research --env backtest --symbol USDJPY --strategy failed_spike_reversal --from 2024-08-01T00:00:00+00:00 --to 2026-08-29T00:00:00+00:00 --seed 42 --param horizon_exit_enabled=true --out reports/h4_with2
python -m trading.backtest.research --env backtest --symbol USDJPY --strategy failed_spike_reversal --from 2024-08-01T00:00:00+00:00 --to 2026-08-29T00:00:00+00:00 --seed 42 --param horizon_exit_enabled=false --out reports/h4_without2
python -m trading.backtest.ablation_compare --with reports/h4_with2/<run_id> --without reports/h4_without2/<run_id> --param horizon_exit_enabled --seed 42
```

同じ結果と言えるのは、両腕の `manifest.json` で `ablation_compare.COMPARABLE_FIELDS` の全項目が本ノートの run と一致するときである。対象は `git_commit` / `git_dirty` / `git_diff_sha256` / `python_version` / `environment` / `symbol` / `strategy_id` / `strategy_version` / `engine_version` / `scenario` / `seed` / `tick_count` / `period_from` / `period_to` / `warmup_days` / `broker_server_ahead_of_ny_hours` / `dataset_hash` / `feature_dataset_hash` / `swap_dataset_hash` の 19 項目。比較 CLI が冒頭に出すのはこのうち一部だけなので、残りは上記 run ディレクトリの `manifest.json` を正本とする。`config_sha256` は腕ごとに違う（「データ」節）ので、照合するのは同じ腕どうしに限る。

3 番目のコマンドは本ノートの run では `verify_comparable` で停止する。主判定に使った有効側の CI90 は、`ablation_compare.load_run` で有効側の run を読み、`ablation_compare.arm_summary` に seed 42 で渡して求めた。
