対象: `post_event_failed_breakout`（USD/JPY、intraday）

## 訂正（2026-09-14）

本ノートは、両腕が指定期間 2024-08-01〜2026-08-29 の全体にわたって取引を重ねた前提で書いた。H4 の測定をきっかけに両腕の run 成果物（`trades.csv` と `summary.json` の `risk_rejections`）を月別に数え直したところ、この前提は成り立っていなかった。判明した事実は 3 つある。

1. **建玉があったのは 25 か月中 12 か月で、残る 13 か月は両腕とも 0 件。** 月別の件数は `trades.csv` の `entry_at`、つまり建てた時刻で集計している。建玉の月が空白ということは、その月に新規建玉が 1 度も通らなかったという意味である。決済（`exit_at`）の月で数え直しても分布の形は変わらず、動くのは月境界をまたいだ建玉が各境界で 1 件ずつだけだった。リプレイ自体は保存 tick を最後まで回し、建玉を保有している間も equity と drawdown を更新している（`backtest/engine.py` の tick ループと `_settle_close`）。空白は「リプレイが途中で止まった」ことを意味しない。
2. **空白 11 か月（2025-02〜2025-12）の原因は銘柄あたりの建玉上限で、口座水準の 3% 停止ではない。** 空白の各月にも `MAX_OPEN_POSITIONS_PER_SYMBOL` の棄却が両腕とも毎月記録されている。signal は毎月出ていて、`RiskEngine` まで届いたうえで枠が埋まっているという理由で落ちていた。この戦略には時間切れ決済が無いので、損切りにも利確にも当たらない建玉が銘柄あたり 1 本の枠を占め続け、次の setup を通さなかった。一方、口座水準の 3% 停止（含み損益込みの資産が最高値から 3% 下がると新規建玉を承認しない規則。棄却コードは `risk/engine.py` の `HWM_DRAWDOWN_WITHIN_LIMIT`）は、確認ありが全期間で 0 件、確認なしが run の最終月 2026-08 の 99 件だけだった。最大ドローダウンは 30,115.26 と 30,250.84 で、初期資金 100 万の 3% にあたる 30,000 を超えている。それでも空白 11 か月には停止が掛かっていない。この規則は絶対額ではなくその時点の高値に対する割合で判定され、signal が出て `RiskEngine` が評価されたときにだけ棄却が記録されるためで、最大ドローダウンの額は停止の証拠にならなかった。残る 2 か月（2026-02〜2026-03）は事情が違い、市場記録そのものが無い。実行計画（`tasks/h5-macro-confirmation-ablation.md`）に記録したとおり、使った tick には 2026-01-23〜2026-04-08 の 74 日欠損があり、research engine は期間途中の欠損を検出せずに次の tick へ飛ぶ。この 2 か月は棄却の記録も無く、評価自体が走っていない。
3. **件数差 203 は、建玉の月で見ると 4 か月に集中している。** 2024 年 9〜11 月で確認なしが 218 件多く、2026-08 で確認ありが 15 件多い。残る 8 か月は両腕の件数が完全に同一だった。ただし月合計が同じでも、レッグが落とした setup の代わりに別の setup が建っていれば同数になるので、同数であること自体は両腕が同じ建玉をたどった証拠にはならない。

判定そのものは変わらない。事前登録の規則による「判定不能（差が検出できない）」は覆らず、両腕とも損失で昇格根拠が無いことも変わらない。判定時に「次のステップ」へ書いた micro_live overlay での降格は、その後 `config/micro_live.yaml` へ `status: SHADOW` として反映済み。これも維持する。変わるのは、この判定がどれだけの標本に立っているかという射程と、空白の原因である。239 / 442 件は 25 か月に散っておらず、建玉が 12 か月に固まっている。それ以外の月は、tick の無い 2 か月を除いて、毎月シグナルが出たうえで建玉上限に落ちていた。月別の件数と棄却の内訳は「データ」節の表に置き、影響する記述は「データ」「結果」「解釈」「教訓」「次のステップ」の各節で書き直した。実測値（件数・損益・CI90・ハッシュ）はそのまま残している。

## 背景

H5 は「日中の failed breakout にマクロ確認（米 2 年金利の 1 日・5 日ドリフト、BOJ 声明スコア）を加えると質が上がる」という仮説。確認レッグは棄却済みの H1（日米の政策収斂が円高を予測する）と同じ金利差情報を使っているため、H1 棄却後は寄与を疑う必要があり、レッグの寄与を分離して測ることにした（PR #124 で ablation ハーネスを追加）。

## 方法

同じ保存 tick・同じ期間・同じ seed で、`macro_confirmation_enabled` を true / false にした 2 本の research リプレイを流し、`trading.backtest.ablation_compare` で約定ごとの純損益を比べる。

判定規則は実行前に固定した（`ablation_compare.judge`、上から順に評価）:

| 条件 | 判定 |
|---|---|
| 確認ありの平均が高く、差の CI90 下限が 0 より大きい | 維持（寄与あり） |
| 確認なしの約定数が 2 倍以上で、平均が確認あり以上 | 外す（絞るだけで質が上がらない） |
| どちらかの腕の約定が 10 件未満 | 判定不能（標本不足）。維持したまま再測定 |
| それ以外 | 判定不能（差が検出できない）。維持したまま再測定 |

差の CI90 は bootstrap（`BOOTSTRAP_SAMPLES` 回、seed 42）。部分決済は 1 エントリーを 1 標本に集約する（issue #126、PR #140）。両腕の共通注文には同じ執行ショックを割り当てる（issue #125 / #134、PR #129 / #140）ので、差に執行ノイズの引き直しは混ざらない。

## 判定

規則を上から当てると次のとおり。確認ありの平均は高いが差の CI90 下限が負なので「維持」にならない。確認なしの約定数 442 は 2 × 239 = 478 に届かず「外す」にもならない。両腕とも 10 件以上なので、**「判定不能（差が検出できない）」** に落ちる。

## 解釈

判定は H5 について「分からない」だが、出力には H5 より重要な事実が 2 つある。

1. **戦略はどちらの腕でも損失。** 確認なしは平均 −50.42 で CI90 が 0 を外し、明確に負。確認ありは平均 −39.03 で CI90 が 0 を含むが、点推定は負で、239 件中の勝ちが約 3 件しかない。初期資金 100 万に対して −0.93%（確認あり）と −2.23%（確認なし）。金利（carry）は両腕とも未値付け（`carry_total=0`、`unpriced_rollovers` 650 件超）で成績に含まれていない。carry の符号は建玉の方向と曜日で受取にも支払にもなるため、含めたときに良化するか悪化するかは不明。
2. **確認レッグは腕全体の損失を減らすが、優位性を作らない。** 腕全体の合計差は −12,960（確認なしが悪い）だが、これは建玉が 12 か月に固まった 239 / 442 件の合計で、25 か月に散った標本の差ではない。件数差 203 も期間全体には散らばっておらず、2024 年 9〜11 月の 3 か月で確認なしが 218 件多く、2026-08 では逆に確認ありが 15 件多い。残る 8 か月は両腕の件数が完全に同一だった。ただし月合計が一致することは、その月に両腕が同じ建玉をしたことまでは意味しない。レッグは setup を落とすことしかできないが、落ちた分だけ建玉の枠と equity の経路が変わるため、代わりに別の setup が建てば月合計は一致しうる。2026-08 で確認ありのほうが 15 件多いのも、同じ経路の変化として説明できる。同じ理由で、確認ありの 239 件が確認なしの 442 件の部分集合であるとも限らない。`RiskEngine` の銘柄別ポジション上限と、現在 equity に依存する sizing によって後続のエントリー集合と数量が変わるためで、合計と件数の差から「落とされたトレード」の成績を逆算することはできない。月別件数が一致した 8 か月で両腕が同じ建玉をたどったかどうかも、部分集合かどうかも、確かめるには両腕の `entry_id` を照合する必要があり、本ノートでは行っていない。確かなのは、通した 239 件の勝ちが約 3 件しかなく、決済の 236 / 239 が protection fill だという事実。

つまり H5 の「質が上がる」は、腕全体の損失を減らすという意味では否定されないが、取引可能な優位性になるという意味では裏付けられない。確認ありの平均 CI90 も腕間差の CI90 も 0 をまたぐので、この結果だけでは検出力不足と優位性不在を区別できず、「優位性が無い」とまでは言えない。言えるのは **`post_event_failed_breakout` を live へ昇格させる根拠が現時点で無い**ことまで。

「維持したまま再測定」は、何を再測定するかで意味が変わる。seed は 2 種類ある。比較 CLI の `--seed` は bootstrap の再標本化に使う乱数系列を選ぶだけで、変えても CI の値が乱数誤差の範囲で揺れるだけで、精度は上がらず差そのものも動かない（精度を上げるのは `BOOTSTRAP_SAMPLES` を増やすこと）。一方、research の `--seed` は `ExecutionSimulator._shock_rng()` に入って reject・slippage・partial fill を決める。安定注文キーで共通注文のショックは腕をまたいで揃えてあるが、片腕にしか無い注文と、約定後の状態遷移には執行乱数が残る。**本ノートは research seed を 1 組（42）しか測っていない**ので、差の分散のうち執行由来がどれだけかは判定できていない。再測定するなら、対応した research seed を複数ペア流して執行感応度を確かめるのが先で、これは腕 2 本を並列で流すだけなので安い。標本を増やす意味での再測定は、時間を待って期間を延ばすより先に、建玉が 12 か月にしか立たない理由を潰すほうが効く。その理由は測定で分かっていて、損切りにも利確にも当たらない建玉が銘柄あたり 1 本の枠を占め続けたことである。これは戦略とリスク条件の問題で、決済のほぼ全部が protection fill になっている構造（利確・損切りの設計）と地続きである。2026-02〜2026-03 だけは tick そのものが無いので、バックフィルでしか埋まらない。

## 教訓

- **ablation の 2 腕は並列で流す。** 逐次で流した 1 回目は、1 本目の実行中に collector が `INTERVENTION_GOVERNMENT_CONFIRMED`（known_at 2026-08-03、窓の内側）を書き込み、`feature_dataset_hash` が食い違って比較が拒否された。fingerprint は実行開始時に固定される（`StoredFeatureSource.frozen`）ので、腕ごとの開始時刻が数時間ずれるとその間の PIT 行の変化がそのまま差になる。ガードは正しく働いた。
- 両腕を流す前に、YAML 由来の collector（policy / intervention）を流し切り、`fx-macro` を止める。tick / bar のタスクは止めない（fingerprint に入らず、止めると系列に穴が空く）。
- PR #140 で `trades.csv` に `entry_id` が入り、それ以前の run は比較 CLI で読めなくなった（`SystemExit: no entry_id`）。ハーネスを変えたら両腕を取り直す。
- **入力条件の一致は、標本が指定期間に散っていることまでは保証しない。** commit・`dataset_hash`・`feature_dataset_hash`・指定期間の一致が言うのは、両腕に同じ入力を与えたことだけ。H5 では建玉が 25 か月中 12 か月に固まり、件数差は 4 か月に集中していたが、比較 CLI の検証は通り、本ノートも期間全体に散った標本として書いてしまった。比較の前に `trades.csv` を `entry_at` の月で数える。決済の月では、建玉を持ち越した分だけ時期がずれる。ただし建玉の月でも分かるのは件数差の出た時期までで、レッグが setup を落とした時期そのものは setup 時刻とゲートの判定結果を見ないと分からない。
- **空白月の原因は `risk_rejections` の棄却コードを月別に見て切り分ける。** 建玉の月が空白でも、シグナルが出ていないのか、出たうえで棄却されたのかは `trades.csv` だけでは分からない。H5 では空白 11 か月のすべてに `MAX_OPEN_POSITIONS_PER_SYMBOL` の棄却が並び、`HWM_DRAWDOWN_WITHIN_LIMIT` は同じ 11 か月に 1 件も無かったので、空白の原因は枠の占有で口座水準の 3% 停止ではない、と決着した。本ノートは最初、空白をリプレイの打ち切りと書き、次に建玉上限と 3% 停止の両論併記に直したが、どちらも棄却コードを見ずに書いたものだった。最大ドローダウンの額のような間接的な指標を、停止が掛かった証拠として使わない。

## 次のステップ

- H5 は「差が検出できない」で閉じる。空白 11 か月には両腕とも毎月 `MAX_OPEN_POSITIONS_PER_SYMBOL` の棄却が記録されているので、銘柄あたりの建玉上限が効いていたことは確かである。ただし日次と 24 時間の損失停止の 2 コードは数えていないので、同時に掛かっていた可能性は残る。この 2 つが掛かっていれば、時間切れ決済で枠を空けても新規建玉は拒否され続ける。残る 2 コードは同じ run 成果物を数え直すだけで分かるので、次の測定条件を決める前にこれを済ませる。そのうえで建玉上限だけが効いていたなら、標本を増やす手は、保有が想定ホライズンを超えたら決済する時間切れ決済を両腕で有効にして流し直すことになる。枠を占め続けた建玉を解放するのはこれだけである。研究リプレイで口座水準の損失停止を掛けない変更（[ADR-037](../adr/ADR-037-backtest-account-level-loss-halts.md)、`config/backtest.yaml` で採用済み）だけでは空白は埋まらないと見ている。元の run では空白 11 か月に 3% のドローダウン停止が 1 件も記録されていないからである。ただし日次と 24 時間の 2 つの停止は今回数えていないので、それらが空白に効いていた可能性は残る。ただしこれは元の run についての事実で、次の run にそのまま持ち越せない。時間切れ決済で枠が空けば取引が増え、equity と最高値の経路が変わるので、元の run では停止が掛からなかった月に掛かることがある。増えた約定を時間切れ決済だけの効果として読みたいなら、時間切れ決済だけを入れた run を分けて流す。いずれにせよこれは同じ条件での測り直しではなく戦略とリスク条件を変えた別の測定なので、H5 の判定を上書きする材料には使わない。2026-02〜2026-03 は tick の 74 日欠損（2026-01-23〜2026-04-08）が原因なので、期間として埋めるにはバックフィルが要る。再測定は VPS で行う。
- `post_event_failed_breakout` は昇格させない。判定時点では `config/micro_live.yaml` がこの戦略を MICRO_LIVE 段階のままにしていたが、issue #146（PR #147）で `status: SHADOW` へ降格済みで、`--env micro_live` で起動しても実注文は出ない。昇格の再判断は、protection fill 偏重の決済構造を直したうえで改めて測ってから。
- 研究資源は H4（failed spike reversal の基礎エッジ、Model A）へ移す。
- 金利コストの未モデル化（issue #60、swap の PIT 収集）は、intraday でも 650 件超のロールオーバーをまたいでいるので、次の判定までに接続する。

## 再現

VPS で YAML 由来の collector（policy / intervention）を先に流し切り、`fx-macro` だけを止めたうえで（tick / bar / account / shadow のタスクは止めない）、2 つのターミナルからほぼ同時に:

```
python -m trading.backtest.research --env backtest --symbol USDJPY --strategy post_event_failed_breakout --from 2024-08-01T00:00:00+00:00 --to 2026-08-29T00:00:00+00:00 --seed 42 --out reports/h5_with3
python -m trading.backtest.research --env backtest --symbol USDJPY --strategy post_event_failed_breakout --from 2024-08-01T00:00:00+00:00 --to 2026-08-29T00:00:00+00:00 --seed 42 --param macro_confirmation_enabled=false --out reports/h5_without3
python -m trading.backtest.ablation_compare --with reports/h5_with3/<run_id> --without reports/h5_without3/<run_id> --param macro_confirmation_enabled --seed 42
```

同じ結果と言えるのは、両腕の `manifest.json` で `ablation_compare.COMPARABLE_FIELDS` の全項目が本ノートの run と一致するとき ―― `git_commit` / `git_dirty` / `git_diff_sha256` / `python_version` / `environment` / `symbol` / `strategy_id` / `strategy_version` / `engine_version` / `scenario` / `seed` / `tick_count` / `period_from` / `period_to` / `warmup_days` / `broker_server_ahead_of_ny_hours` / `dataset_hash` / `feature_dataset_hash` / `swap_dataset_hash`。比較 CLI の冒頭に出るのはこのうち一部だけで、残りは上記 run ディレクトリの `manifest.json` を正本とする。`config_sha256` も manifest に記録されるので、あわせて照合する。

なお、上記の run は [ADR-037](../adr/ADR-037-backtest-account-level-loss-halts.md) より前のもので、`config/backtest.yaml` に口座水準の損失停止の無効化が入る前の設定で流している。以降の run と直接比較しない。
