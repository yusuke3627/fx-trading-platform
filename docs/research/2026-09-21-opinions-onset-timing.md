# 大きく動いた回は、公表の瞬間に動き出したか（段階3b-1）

- 登録日 / 測定日: どちらも 2026-09-21（事前登録をコミット `1baa850` で先に固定してから測り、判定規則と閾値は測定後に変えていない）
- 判定: **`not_established`。公表直後の 1 分に最大の値動きが集まる形は無かった。** `k* = 0` の事象は 1 / 20 で、曜日構成を揃えた期待件数 1.31 を下回る。欠測 0 / 20、対照 227 日。段階3b で上側に来た 5 件も、ひとつも公表の瞬間に動き出していない。ただし事前登録していない形として、**事象の `k*` は 15 / 20 が公表後（`k* ≥ 0`）に寄っていた**（対照は 111 / 227 = 0.489、曜日構成を揃えた期待は 9.61）。この形からは判定を出さず、新しい標本で評価する規則として登録した
- 対象: 段階3b と同じ BOJ 20 会合ぶんの主な意見の公表と、同じ対照日
- ハーネス: [opinions_onset_study.py](../../src/trading/data/policy/opinions_onset_study.py)
- 前段: [段階3b のイベントスタディ](2026-09-20-opinions-market-reaction-event-study.md)

## なぜこれを測るのか

段階3b の判定は `not_established` だった。公表直後 10 分の値動きは、同じ曜日のふだんの朝と中央値では区別がつかない。ただし 20 件中 5 件が同曜日対照の 90 パーセンタイルを超えており（帰無の期待は 2 件）、**「ほとんどの回は何も起こらないが、まれに大きく動く」可能性だけが残った。**

その 5 件のうち 3 件は 2024 年 4〜9 月に集まっている。為替介入と円キャリー巻き戻しの時期で、公表とは無関係に地合いが荒れていた。段階3b の測り方では、**大きく動いたのが公表のせいなのか、当時の地合いなのかを分けられない。**

分ける方法がひとつある。**動き出した時刻を見ることだ。** 公表が原因なら、値動きは 08:50:00 から始まる。地合いが原因なら、始まる時刻は窓の中でばらける。段階3b は窓全体のリターンしか見ていないので、この情報を使っていない。

副産物として、段階3b の限界のひとつも潰せる。`t0` は声明が予告する「予定」時刻であって実公表時刻の記録ではない、と書いた。事象の動き出しが 08:50:00 に集まるなら、予定時刻は実公表時刻として使えていたことになる。

新しいデータは要らない。段階3b で取得した tick のキャッシュ（502 ファイル）をそのまま使う。費用はゼロ。

## この測定が答えないこと

収益性、執行可能性、Data Upgrade Gate の通過。反応の大きさも測らない。**測るのは「いつ動き出したか」だけである。**

## 窓と刻み

`t0` は段階3b と同じで、声明 PDF が予告する公表時刻（20 件すべて 08:50 JST = 23:50 UTC 前日）。

窓は **`[t0 - 10分, t0 + 10分)`** とし、1 分刻みで 20 個の区間に割る。区間 `k` は `[t0 + k分, t0 + (k+1)分)` で、`k` は −10 から 9 まで。`k = 0` が公表直後の 1 分間である。

窓を `t0 + 10分` で切るのは、**その時刻が 09:00 JST、東京株式市場の寄り付きにあたるから**である。ここには公表と無関係の構造的なボラティリティの山がある。窓に入れると最大値がそちらに持っていかれて検定が鈍る。測定後に「9:00 の区間を除く」と決めるのは後付けになるので、**窓の端に置いて最初から入れない。**

前後を 10 分ずつの対称にしたのは、公表前にも同じだけの「動き出しうる時間」を与えるためである。

各区間のリターンは対数リターン `log(p1 / p0)` で、価格は**その時刻より厳密に前で最後の tick** の中値。区間内に tick が無ければリターンは 0 になる（観測できる範囲で価格が動いていない）。

> **訂正（2026-09-21、測定後）**: 登録時のこの一文は「その時刻**以前**で最後の tick」と書いており、上の半開区間 `[t0 + k分, t0 + (k+1)分)` の定義と矛盾していた。実装も「以前」で書かれていたため、境界ちょうどの tick が直前の区間へ入っていた（PR #206 のレビュー指摘）。**規則として生きているのは半開区間の定義のほう**なので、文と実装をそちらへ揃えた。実データへの影響は結果節に書いたとおり無い（run-2 と run-3 で全数値が一致）。閾値・窓・主統計は変えていない。

## 主統計

各日について、20 区間のうち `|リターン|` が最大の区間を選ぶ。これを **オンセット `k*`** と呼ぶ。

- 最大値が複数の区間で並んだ場合は、**早いほうの区間**を採る
- 20 区間すべてのリターンが 0（窓内でまったく動いていない）なら、その日は `no_movement` として欠測にする

反応が無ければ `k*` は窓の中でばらけ、`k* = 0` になる確率は 1/20 = 0.05 になる。公表が原因で動いているなら、`k* = 0` が事象に偏る。

## 対照群

段階3b とまったく同じ対照日を使う。候補は各公表日の UTC 日付 ±10 日以内で、窓の **JST 日付**が土日・公表日・政策決定日の前後 1 日にあたる日を除く。さらに post10 窓（`[t0, t0 + 10分]`）の tick が 30 件未満の日を流動性欠損として外す。段階3b の実測では候補 231 日から 4 日（JST のクリスマスと元日）が落ちて 227 日だった。

対照集合を段階3b と揃えるのは、2 つの測定を直接比べられるようにするためである。流動性の床を post10 に掛けたままにするのも同じ理由で、この研究のために床を組み替えない。

対照にも 08:50 JST に出る日本の統計が含まれる。**これは利点である。** 「東京の朝 08:50 に何かが公表される」という背景そのものが対照側に入るので、`k* = 0` の対照率はその背景込みの基準線になる。主な意見に固有の効果だけが差として残る。

### 曜日を揃える

段階3b で、公表の JST 曜日が月 8・火 4・水 2・木 3・金 3 と月曜に偏っていること、JST 月曜 08:50 が週明けの寄り付きから 2 時間弱でふだんの平日とは様子が違うことが分かっている。

ただしここで曜日ごとに対照を割ると、1 曜日あたり 45 日前後 × 5% = 2〜5 件しか当たりが出ず、率の推定が荒すぎる。そこで**事象側は 20 件のまま数え、期待値の側で曜日構成を合わせる**。

対照の `k* = 0` の率を曜日ごとに `c_月, c_火, ...` と求め、期待件数を次で定義する。

```
期待件数 = Σ（各事象について、その事象の JST 曜日の対照率）
```

事象が月曜 8 件・火曜 4 件…なら `8·c_月 + 4·c_火 + …` になる。曜日構成を揃えたうえで、事象側の分解能を落とさない。

事象が使う JST 曜日のいずれかで対照が 30 日未満なら、率を推定できないので判定を出さずエラーで止める。

## 主判定

`n0` を、20 件のうち `k* = 0` だった事象の件数とする。

判定は次の順で見る。

1. **`n0 ≥ 4` かつ `n0 ≥ 3 × 期待件数` → `onset_at_publication`**
2. そうでなく、欠測した事象が 1 件以上あれば → `incomplete`
3. どちらでもなければ → `not_established`

欠測した事象は `n0` に寄与しない（数えられない＝当たっていない扱い）。欠測は `n0` を下げる方向にしか効かないので、**1 が成立するなら欠測があっても確定してよい。** この順序は段階3a のレビュー指摘（#196）と段階3b の主判定に揃えてある。欠測があっても確定できるのは、欠測が不利に転んでも成立する側の判定だけである。

### 閾値の根拠

**`n0 ≥ 4` の床。** 帰無の率 0.05 のとき 20 件中 4 件以上が出る確率は約 1.6% である。また 4 件あれば 1 件落としても 3 件残り、1 回のエピソードで結論が決まらない（`policy_event_study.py` が「エピソードを 1 つ落としても残るか」を読むと定めているのに合わせる）。

**`3 ×` の倍率。** 対照率が背景の 08:50 公表を含んでいる以上、帰無は 0.05 より高くなりうる。倍率で書いておけば、対照率が高く出た場合に自動で閾値も上がる。

p 値は出さない。段階3b・`policy_event_study.py` と同じ方針で、この標本数の p 値は見世物にしかならない。

`not_established` は「公表の瞬間に動き出していない」ではない。n = 20 で不在は示せない。

## 記述として併記するもの

- **`k*` のヒストグラム**（事象・対照、20 区間ぶん、件数と率）。主判定が何を見ているかはこれで分かる。`k* = 0` 以外に山があればそれも見える
- **段階3b で上側に来た 5 件の `k*`**（会合日 2024-04-26 / 2024-07-31 / 2024-09-20 / 2025-06-17 / 2025-09-19）。**この 5 件は段階3b の結果を見てから選んだ事後の部分集合である。** 判定には使わず、記述として出す。この測定が答えたかった「大きく動いた回は公表の瞬間に動き出したのか」に最も近い数字がこれなので、選び方を明記したうえで載せる
- **`k* = 0` だった事象の、分 0 の中の 10 秒バケット 6 個のうち最大の位置。** 動き出しが 08:50:00 の直後なのか分の後半なのかが分かる。実公表時刻の経験的な当たりになる
- **1 件落としの頑健性。** どの 1 件を落としても主判定が変わらないか
- **対照の `k* = 0` 率（全体と曜日別）**

## 先に宣言しておく限界

1. n = 20
2. `k*` は「窓内で最も動いた 1 分」しか見ない粗い統計である。**本物だが小さい反応が 20 分窓の最大を取らない場合、この測定には映らない。** 反応の大きさはここでは測らない
3. 08:50 JST に出る日本の統計は事象側にも対照側にも入る。対照率がそれを吸収するので基準線としては正しいが、事象の `k* = 0` が主な意見によるのか同時刻の統計によるのかは分けられない。手元に 2024〜2026 の日本の経済カレンダーが無い
4. 09:00 JST 以降に現れる反応は窓の外なので測らない。東京の寄り付きを待って動く種類の反応は対象外である
5. `t0` は予告された予定時刻である。実公表がずれていた場合、`k*` はそのぶんずれた位置に出る。記述の 10 秒バケットはそれを見るためのものだが、ずれが分をまたぐ規模なら主判定は取り逃す

## 結果

run-3（`tmp/opinions-onset/run-3`）。段階3b のキャッシュ 502 ファイルをそのまま使い、ネットワーク
へは出ていない。費用ゼロ、解析は数秒。対照候補は段階3b と同じ 231 日、除外後 227 日。

run-2 との違いはレビュー指摘（PR #206）で直した区間境界の扱いだけである。事前登録は区間を
`[t0 + k分, t0 + (k+1)分)` と半開で定義しているのに、実装は境界ちょうどの tick を**直前の**区間へ
入れていた。公表時刻ちょうどに動いた回があれば `k = 0` ではなく `k = -1` に落ちるため、この研究で
最も重要な境界を取り違える。各境界の価格を「その時刻より厳密に前の最後の tick」に揃えて直した。
規則の変更ではなく、実装を登録した定義に合わせる修正である。

実データでは 247 日のうち公表時刻ちょうどに tick があるのは 4 日で、すべて対照、事象は 0 件だった。
**run-2 と run-3 で主判定・事象ごとの `k*`・対照の `k*`・10 秒バケットのすべてが一致している。**
今回の結論は動かないが、将来の検定 B ではこの境界が効く。

### 主判定: `not_established`

| | 値 |
|---|---|
| `k* = 0` だった事象 `n0` | **1 / 20** |
| 曜日構成を揃えた期待件数 | 1.3090 |

| 2024-07-31 | 2024-08-08 | 7 |

**公表の瞬間に動き出した回はひとつも無い。** ただし 5 件すべてが公表より後（`k* ≥ 0`）に来ている。

### 事後に気づいた形（判定は出さない）

事前登録した記述のヒストグラムを見ると、事象の `k*` は `k = 2, 3, 5, 7` に固まっている。

| | `k* < 0`（公表前） | `k* ≥ 0`（公表後） |
|---|---:|---:|
| 事象 | 5 / 20 | **15 / 20** |
| 曜日構成を揃えた期待 | 10.39 | 9.61 |
| 対照 | 116 / 227 | 111 / 227（0.4890） |

対照はほぼ半々なのに、事象は 4 分の 3 が公表後に寄っている。**最大の 1 分が公表の直後ではなく、
1〜7 分後に来る。** 数ページの PDF を読んで消化するのに数分かかる、という筋書きと整合する。

**この形は事前登録していない。閾値も無い。だからここから判定は出さないし、同じ 20 件で検定し直す
こともしない。** 主判定は `not_established` のままである。段階3b の 5 / 20 と同じで、標本を見てから
目に入った形にその標本で合格点を出すことはできない。規則は
[段階3b-2 の文書](2026-09-21-opinions-tail-frequency-protocol.md)に固定し、新しい会合で評価する。

### 段階3b との関係

段階3b は「公表後 10 分のリターンの大きさ」を測って `not_established` だった。今回は「その 10 分の
どこで動いたか」を測って、やはり公表の瞬間ではなかった。**大きさでも瞬間でも、公表に結びつく像は
出ていない。**

ただし上の事後の形が本物なら、2 つの結果は両立する。公表は朝の値動きの**大きさ**を変えず、**いつ
起きるか**だけを後ろへずらしている、という読み方になる。これは仮説であって、この測定の結論ではない。

### 対照の `k*` に見えた説明できない山

対照の `k* = -5`（08:45 JST）が 33 / 227 = 0.1454 と、他の区間（0.02〜0.07）より明らかに厚い。
理由は分からない。事象側は 1 件だけなので主判定には効いていないが、**対照の分布が一様でないこと
自体は記録しておく。** これが市場の性質なのか Dukascopy の癖なのかは調べていない。

### この測定が言うこと・言わないこと

言うこと。**公表直後の 1 分に値動きが集中する形は無かった。** 段階3b で上側に来た 5 件も、公表の
瞬間には動き出していない。

言わないこと。公表時刻に反応が無いことは示していない（n = 20 で不在は示せない）。`k*` は「窓内で
最も動いた 1 分」しか見ない粗い統計なので、本物だが小さい反応は映らない。09:00 JST 以降に現れる
反応も窓の外である。収益性・執行可能性・Data Upgrade Gate の通過も判定していない。

`t0` が予定時刻である件は、**結局解消していない。** `k* = 0` が 1 件では実公表時刻を推定できない。
事後の形（1〜7 分後に寄る）が読み込み時間なのか公表の遅れなのかも、この測定では分けられない。
